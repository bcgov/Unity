01

The pattern

Grant programs need custom intake questions and custom assessor scoring criteria, and those requirements change per-program and over time. Without Flex, every new question or scoring criterion would mean a code change, a migration, and a deployment. Unity.Flex turns "define a form field" and "define a scoring question" into an admin-configurable, runtime action: a program admin builds a Worksheet (custom data-collection form) or a Scoresheet (assessment/scoring form) through a UI, publishes it, and the rest of the system renders and stores data against it — no code change required.

It does this with a deliberately generic, reusable pattern that shows up twice in the module:

01 · Definition
Worksheet → WorksheetSection → CustomField Scoresheet → ScoresheetSection → Question
02 · Instance
WorksheetInstance one per target record ScoresheetInstance one per assessor, per record
03 · Value
CustomFieldValue jsonb, keyed by field Answer jsonb, keyed by question

Both definitions and values live as JSON, not fixed columns — new fields ship without a migration. A generic (CorrelationId, CorrelationProvider) pair — not a foreign key — attaches an instance to whatever record owns it, so Flex never depends on the host module's schema.

Glossary

WorksheetAdmin-defined custom data-collection form template (e.g. "Project Details"). Made of sections and fields.

ScoresheetAdmin-defined assessment/scoring form template (e.g. "Standard Assessment Scoresheet"). Made of sections and questions.

02

Module architecture

Unity.Flex is a self-contained ABP module (its own solution file, Unity.Flex.abpsln) referenced by the host Unity.GrantManager solution — never the reverse. It follows the standard ABP layering used across this codebase.

Unity.Flex.Shared (field/question enums, Definitions, Values, ChefsToUnityTypes — no ABP dependency) ↑ Unity.Flex.Application.Contracts (DTOs, app service interfaces) ↑ Unity.Flex.Application (entities, domain services, EF Core, app services, controllers, event handlers, reporting generators) ↑ Unity.Flex.Web (Razor Pages admin builder + ViewComponents runtime widgets)

Unity.GrantManager.Application / .Domain depend on Unity.Flex.Application.Contracts (and, for the ETO-publishing side, Unity.Flex.Shared) to talk to Flex — never the reverse. The two modules are decoupled at runtime through ABP local events rather than direct app-service calls (see §08).

Other modules that reference Flex types (seen in test-bin output): Unity.Notifications, Unity.Payments, Unity.Reporting.

Feature flag, not permission

Unity.Flex has no dedicated ABP permission definitions of its own (FlexMenus.cs is an empty stub). Access is entirely delegated to the host application — see §10 for the full breakdown. In short: a tenant can be switched off Flex entirely via the Unity.Flex tenant feature; the host module falls back to a legacy, hardcoded scoresheet mechanism when it is disabled (see §09).

Domain model

Two parallel sub-systems share one architectural pattern — definition → instance → value — implemented independently for worksheets and scoresheets.

Aggregate roots

Aggregate rootBase typeOwns
WorksheetFullAuditedAggregateRoot<Guid>Sections (→ CustomFields)
WorksheetLinkAuditedAggregateRoot<Guid>— (attaches a Worksheet to a UI anchor on an external entity)
WorksheetInstanceFullAuditedAggregateRoot<Guid>CustomFieldValues
ScoresheetFullAuditedAggregateRoot<Guid>Sections (→ Questions), Instances
ScoresheetInstanceFullAuditedAggregateRoot<Guid>Answers

Child entities (WorksheetSection, CustomField, CustomFieldValue, ScoresheetSection, Question, Answer) are owned via conventional EF HasMany/HasForeignKey — not true EF owned-entity ownership. CustomFieldValue is only AuditedEntity (no soft delete); every other entity is full-audited, plus standard ABP ExtraProperties/ConcurrencyStamp, and all implement IMultiTenant.

Worksheet template tree

Worksheet 1─* WorksheetSection 1─* CustomField
WorksheetDomain/Worksheets/Worksheet.cs

Named, versioned, publishable/archivable form template.

WorksheetSectionDomain/Worksheets/WorksheetSection.cs

Named, ordered group of fields.

CustomFieldDomain/Worksheets/CustomField.cs

One field: name/key/label/type/order/enabled + a JSON Definition describing type-specific config (options, required-ness, etc.).

In-memory invariants enforced by the aggregate (not DB constraints):

  • Worksheet.SetTitle throws UserFriendlyException("Blank titles are not allowed") on empty title.
  • Worksheet.AddSection throws UserFriendlyException("Section names must be unique") on a duplicate section name within the worksheet.
  • WorksheetSection.AddField / CustomField.SetKey throw on a duplicate field Name — checked across the whole worksheet, not just the owning section.
  • CustomField.Name is auto-derived: custom_<worksheetname>_<key> (CustomField.ConfigureName). This is the stable machine name used for JSON lookups, and the naming convention that WorksheetsManager.CreateWorksheetDataByFields parses back apart (splitting on _) when bulk-creating instances from a flat field list.
  • Order (uint, 1-based) is assigned automatically on add, append-only. No reorder validation at the domain layer — resequencing is an app-service concern (ResequenceSectionsAsync, ResequenceCustomFieldsAsync).

Worksheet instance tree & correlation

WorksheetInstance 1─* CustomFieldValue
WorksheetInstanceDomain/WorksheetInstances/WorksheetInstance.cs

One filled instance of a Worksheet. Holds a rolled-up CurrentValue JSON blob plus the individual CustomFieldValues. AddValue(customFieldId, currentValue) appends a new value.

CustomFieldValueDomain/WorksheetInstances/CustomFieldValue.cs

One field's value, JSON-typed, tied to CustomFieldId by ID only (no navigation property — a child of one aggregate referencing another aggregate's descendant by ID, per the "reference other aggregates by ID" DDD convention used throughout this codebase).

Both WorksheetInstance and WorksheetLink implement ICorrelationEntity (Unity.Modules.Shared.Correlation), giving them a generic (CorrelationId, CorrelationProvider) pair instead of a hard foreign key:

  • WorksheetLink.CorrelationId/CorrelationProvider + UiAnchor + Order + WorksheetId define where and how many times a worksheet template is mounted onto a target entity.
  • WorksheetInstance.CorrelationId/CorrelationProvider identifies the target record the filled-in data belongs to (e.g. the Application itself).
  • WorksheetInstance.WorksheetCorrelationId/WorksheetCorrelationProvider additionally correlates back to the link that placed the worksheet — distinguishing "which mounting of the worksheet is this instance for."
  • WorksheetInstance.UiAnchor records which named UI slot the instance belongs to.

UI anchor constants live on the host side, not in Flex itself — see §09.

Scoresheet template tree

Scoresheet 1─* ScoresheetSection 1─* Question
ScoresheetDomain/Scoresheets/Scoresheet.cs

Named/titled, versioned, publishable, ordered. Also has a direct Instances navigation collection (unlike Worksheet, which only relates to its instances via correlation).

ScoresheetSectionDomain/Scoresheets/ScoresheetSection.cs

Named, ordered group of questions.

QuestionDomain/Scoresheets/Question.cs

Name/label/description/type/order/enabled + JSON Definition.

Same duplicate-name guards as Worksheet: section names unique per scoresheet (case-insensitive), question names unique across the whole scoresheet. Inconsistency worth knowing: Scoresheet.UpdateSectionName throws a namespaced, localizable BusinessException(ErrorConsts.DuplicateSectionName), while most of the equivalent Worksheet guards (and other Scoresheet guards) throw a plain UserFriendlyException with a hardcoded English string. ErrorConsts.DuplicateFieldName is defined but not observed in use anywhere in the domain layer.

Scoresheet instance tree

ScoresheetInstance 1─* Answer
ScoresheetInstanceDomain/ScoresheetInstances/ScoresheetInstance.cs

One assessor's completed scoresheet. CorrelationId/CorrelationProvider ties it to one external assessment record. Holds a rolled-up serialized Value plus the individual Answers. Direct ScoresheetId FK to its parent Scoresheet — no correlation indirection needed here, unlike worksheets.

AnswerDomain/ScoresheetInstances/Answer.cs

One question's answer, JSON CurrentValue, versioned. FKs to Question via QuestionId with a real navigation property (Answer.Question) — unlike CustomFieldValue → CustomField, which is ID-only.

Required-answer validation

ScoresheetsManager.ValidateScoresheetAnswersAsync(instance, scoresheet) (static) walks every Question in every section; for each Question.IsRequired() (read out of the type-specific Definition JSON via DefinitionResolver.ResolveIsRequired), it checks a matching Answer exists and IsProvided() (non-null/non-empty via ValueResolver.Resolve). Returns human-readable errors like "{sectionOrder+1}.{questionOrder+1}: {label} (required)".

Cloning and versioning

SheetParserFunctions (Domain/Utils/SheetParserFunctions.cs) provides SplitSheetNameAndVersion(name) (splits "myform-v3" into ["myform", "-v3"]) and RemoveTrailingNumbers(input). Used by WorksheetsManager.CloneWorksheetAsync to compute the next version name when cloning (myform-v1 → myform-v2), duplicating every section and field with fresh GUIDs.

Runtime data pipeline — WorksheetsManager

WorksheetsManager (Domain/Services/WorksheetsManager.cs) implements the "fill a worksheet instance from raw field data" pipeline:

  • PersistWorksheetData — handles an event with a flat dictionary of field values, resolves the target WorksheetInstance/Worksheet by correlation or name, converts each raw value via ValueConverter.Convert per field's CustomFieldType, rolls the values into the instance's CurrentValue JSON, and optionally triggers reporting-data generation if the Reporting feature is enabled.
  • CreateWorksheetDataByFields — bulk-creates new WorksheetInstances from a flat field-value list keyed by the custom_<worksheet>_<field> naming convention, guarding against duplicate instance creation.

This is the mechanism by which an external form submission (a CHEFS intake form — see §09) populates a Flex worksheet instance.

Settings and error codes

  • FlexSettingDefinitionProvider defines no settings — an empty override. FlexSettings only exposes GroupName = "Flex". Placeholder/scaffold, not currently used.
  • FlexErrorCodes is intentionally empty. The only real structured errors are in Domain/Exceptions/ErrorConsts.cs: DuplicateSectionName and DuplicateFieldName, and only DuplicateSectionName is actually thrown.
  • PrivateSetterContractResolver, WorksheetContractResolver, ScoresheetContractResolver (Domain/Settings/) are Newtonsoft IContractResolvers that let entities with private setters serialize/deserialize directly — needed because nearly every property on these entities is private set. These back JSON import/export of whole Worksheet/Scoresheet aggregates (see §08).

Definition & value classes

Each field/question type has a matching pair of classes:

  • *Definition (Worksheets/Definitions/) — the type-specific configuration shape: TextDefinition, NumericDefinition, CurrencyDefinition, DateDefinition, DateTimeDefinition, EmailDefinition, PhoneDefinition, RadioDefinition (+RadioOption), CheckboxDefinition, CheckboxGroupDefinition (+CheckboxGroupDefinitionOption), SelectListDefinition (+SelectListOption), QuestionSelectListDefinition (+QuestionSelectListOption, scoresheet-specific), BCAddressDefinition, TextAreaDefinition, DataGridDefinition, YesNoDefinition/QuestionYesNoDefinition. All implement ICustomFieldFormat. DefinitionResolver resolves/serializes the right definition type for a given CustomFieldType/QuestionType.
  • *Value (Worksheets/Values/) — the type-specific stored value shape: TextValue, NumericValue, CurrencyValue, DataGridValue, CheckboxGroupValue (+CheckboxGroupValueOption), BCAddressValue (+BCAddressLocationValue), etc. All extend CustomValueBase, used by ValueConverter/ValueResolver for typed (de)serialization of the JSON-stored field/answer values.

Where it's set — the builder UI

UpsertCustomFieldModal.cshtml/.cshtml.cs is the admin UI, split across two tabs:

  • Display tab — Key, Label, a Label Position toggle (Top/Left), the Type dropdown, a Placeholder input (text-like types only), and the type-specific definition editor.
  • Attributes tab — Security (Classification Level dropdown, with a live tooltip — see below), Visibility (IsHidden/HideLabel/IsDisabled checkboxes), Label (Inline Style + CSS Class text inputs).

Gap: the Label section only exposes LabelStyle/LabelCssClass. There is no builder UI for the base Style/CssClass — rendering fully supports them, but today they can only be set by hand-editing exported/imported worksheet JSON. Wiring two inputs into the Attributes tab is the smallest next step; the plumbing already exists end to end otherwise.

Where it's applied — rendering

All of it is applied in exactly one place, uniformly across every field type, before control passes to the type-specific widget: _WorksheetSections.cshtml.

<div class="worksheet_field {label-left|label-top}{fieldDef.CssClass}" hidden="{fieldDef.IsHidden}" style="{fieldDef.Style}"> <label class="field-label {fieldDef.LabelCssClass}" style="{fieldDef.LabelStyle}">{field.Label}</label> <!-- unless HideLabel --> <fieldset disabled="{fieldDef.IsDisabled}"> <!-- type-specific widget renders the control here --> </fieldset> </div>

Deliberate separation, not an oversight: styling lives on the shared wrapper; none of the ~13 per-type widgets re-read Style/CssClass/LabelPosition themselves. One consequence: custom CSS targeting the bare control has to reach through the wrapper (e.g. .worksheet_field.my-class input), not style it directly.

Security classification — Protected A/B/C

The three levels mirror the BC Government's real information classification standard, with explanatory tooltip copy baked into UpsertCustomFieldModal.js:

ProtectedALow Sensitivity

"If compromised, could cause limited or moderate injury to an individual or organisation — e.g. an exact salary figure or home address."

ProtectedBMedium Sensitivity

"Could cause serious injury if disclosed — e.g. Social Insurance Numbers, employment equity data, or personal health records."

ProtectedCHigh Sensitivity

"The most sensitive level — disclosure could cause extremely grave injury."

This is presentation metadata only — it is not enforced anywhere. Confirmed across the whole solution: SecurityClassification appears in exactly three places — the definition property, the builder modal, and the modal's tooltip script. It is not checked by any app service or permission, not displayed anywhere at runtime, and not factored into reporting/export data.

This is exactly the "sensitivity tier" concept proposed in §12 Roadmap as a way to fit ABP's compile-time permission model to runtime-created fields — except it doesn't need to be designed, it already exists. Only the enforcement layer is missing.

06

DataGrid fields

CustomFieldType.DataGrid — a repeating-row grid — is by far the most complex of the fifteen field types: its own column-population modes, a full CRUD editing surface, auto-sum, and reporting handling distinct from every other type. It earns its own section.

Column population: three modes

A grid's columns come from up to two independent sources, controlled by DataGridDefinition.Dynamic (bool) and DataGridDefinition.Columns (admin-declared Name/Type pairs).

ExplicitDynamic = false

The admin declares Columns up front in the builder, each name unique and validated. The only mode where a new row can be manually added at runtime.

DynamicDynamic = true

Columns are not admin-declared. At CHEFS-intake-mapping time, DynamicDataBuilder.BuildDataGrid walks the live CHEFS form schema, finds the matching datagrid component, and builds the value's own column list (DataGridValue.Columns — distinct from DataGridDefinition.Columns) alongside the submitted row data.

Combinationboth at once

A dynamic grid can also carry explicit DataGridDefinition.Columns. Both the runtime widget and the reporting-metadata parser merge the two: dynamic/CHEFS columns emit first in CHEFS's own order, explicit columns are appended for any key not already present — dynamic wins on collision.

Rendering, editing & auto-sum

  • Editing is universal — AllowEdit is always true. Every row is editable via EditDataRowModal, backed by DataGridReadService (loads current values) and DataGridWriteService (full CRUD: add first row — creating a WorksheetInstance if none exists — add row, update row, delete row; every write re-syncs the parent instance).
  • Adding a new row is restricted — only offered when the grid is not dynamic (GenerateAvailableTableOptions(!Dynamic)). A CHEFS-driven column set isn't something a user can safely append an arbitrary row to. Export is always available.
  • Supported column types — a curated subset: Text, TextArea, Currency, Numeric, Date, DateTime, YesNo, Checkbox, Phone, Email. Formatting (display / storage / input) is type-aware, including browser-timezone correction for DateTime and culture-aware currency formatting.
  • Auto-sum — SummaryOption (None/Above/Below) controls a summary row. Only Numeric and Currency columns are summable, each getting a Total: {ColumnName} field computed by SumCells (decimal sum, strips $/,, clamped at decimal.MaxValue rather than overflowing).

Reporting: dynamic columns are treated differently

In DataGridReportDataGenerator, explicit and dynamic columns diverge:

  • Explicit columns become individual, named report fields — {fieldKey}-{columnName}, same as any other field.
  • Dynamic columns (in the value but not in DataGridDefinition.Columns) are not exploded into individual fields — they're collapsed into one combined JSON blob field, {fieldKey}-DynamicColumns. A variable, CHEFS-driven column set can't map onto fixed SQL columns.

Full detail, including the reporting-metadata resolution path: documentation/flex/flex-datagrid.md.

Database schema

Both Worksheets and Scoresheets tables live in schema Flex, inside the tenant database (FlexDbProperties.ConnectionStringName = "Tenant" → GrantTenantDbContext). No table prefix.

Design notes

  • Schema-per-row / EAV-style design: both field definitions (shape/validation rules) and field values are stored as flexible jsonb rather than fixed relational columns — the mechanism that makes the whole system dynamic without per-form schema migrations.
  • Multi-tenant: every entity implements IMultiTenant (nullable TenantId) — standard ABP row-level tenant filtering.
  • Reporting support: Worksheet and Scoresheet implement IReportableEntity<T> and carry ReportColumns/ReportKeys/ReportViewName text columns, backing a generated-SQL-view mechanism that flattens the dynamic JSON into queryable columns — see §08 and documentation/reporting/.
  • No additional unique indexes/constraints beyond primary keys were found — duplicate-name prevention is purely an application/domain-layer invariant, not DB-enforced.

Command/handler pattern

Flex is driven by ABP local events (ILocalEventHandler<TEto>, ITransientDependency), not direct app-service-to-app-service calls from the host module. The host module publishes an ETO via ILocalEventBus; Flex's own handler performs the actual write. In-process, synchronous-within-request — used purely as a decoupling seam between Unity.GrantManager and Unity.Flex.

Reporting integration

Two parallel pipelines: one for field metadata, one for instance data.

  • Field generators (Reporting/FieldGenerators/) — IReportingFieldsGenerator / ReportingFieldsGenerator / ReportingFieldsGeneratorFactory, with per-type generators (CheckboxGroupReportingFieldsGenerator, DataGridReportingFieldsGenerator, DefaultReportingFieldsGenerator for worksheets; QuestionsReportingGenerator, DefaultFieldsGenerator for scoresheets). WorksheetReportingFieldsGeneratorService / ScoresheetReportingFieldsGeneratorService compute flattened "report keys" (one per section/field/checkbox-option), stored on the entity as ReportKeys / ReportViewName.
  • Data generators (Reporting/DataGenerators/) — ScoresheetsReportingDataGeneratorService.GenerateAndSet(Scoresheet, ScoresheetInstance) builds a keyed dictionary matching each report key to an Answer, converts values via ScoresheetsReportingDataGeneratorFactory, computes TotalScore (summing Number/YesNo/SelectList questions), and serializes onto instanceValue.SetReportingData(json). Wrapped in a blanket try/catch — a failure just logs and skips; report data can be regenerated later. WorksheetsReportingDataGeneratorService/Factory follow the equivalent pattern for CustomFieldValues.
  • Dynamic DB views — WorksheetsDynamicViewGeneratorHandler / ScoresheetsDynamicViewGeneratorHandler call a Postgres stored procedure directly via raw SQL (CALL "Reporting".generate_worksheets_view(@worksheetId)) to materialize a queryable SQL view per published worksheet/scoresheet. This is how Flex's dynamic/JSON-shaped data becomes something Unity.Reporting can query relationally.
  • Sync app services (ops tooling) — IWorksheetReportingFieldsSyncAppService (SyncFields, SyncData) and IScoresheetReportingFieldsSyncAppService (SyncQuestions, SyncAnswers), both [Authorize(ITAdminPolicyName)]. Iterate all tenants and backfill missing report keys/data — not part of the live request path.
PLANNED DIRECTION: auto-generation of dynamic views (one per published worksheet/scoresheet, via generate_worksheets_view()) is scheduled to be removed. Reporting views are planned to move to explicit reporting configuration instead — a view exists where someone has configured one, not automatically for every publish. Stated project direction, not yet implemented.

Import / export

WorksheetImportDto/ExportWorksheetDto and ScoresheetImportDto/ExportScoresheetDto define JSON import/export of an entire worksheet or scoresheet template — sections, fields/questions, and their definitions. The domain-layer contract resolvers (above) make this possible despite nearly every entity property being private set. Exposed over HTTP via the export/import controller endpoints, and in the admin builder UI's clone/publish workflow.

09

Host integration

All integration points below are gated by the ABP tenant feature "Unity.Flex", checked on the host side before publishing any Flex-related local event.

Intake → Worksheet

Unity.GrantManager.Domain/Intakes/CustomFieldsIntakeSubmissionMapper.cs ([IntegrationService], DomainService), method MapAndPersistCustomFields(applicationId, formVersionId, formSubmission, formVersionSubmissionHeaderMapping):

  • Parses a CHEFS form submission's JSON and pulls out fields whose config key is prefixed custom_ (format custom_<worksheetname>.<type>).
  • Resolves each field's CustomFieldType from the suffix.
  • Publishes CreateWorksheetInstanceByFieldValuesEto with SheetCorrelationId = formVersionId, InstanceCorrelationId = applicationId, and the extracted custom fields.

Application → Scoresheet instance creation

GrantApplicationAppService.cs — at two call sites (creation, resubmission/status-change), checks form.ScoresheetId != null && Unity.Flex enabled, then publishes CreateScoresheetInstanceEto. Every application tied to a form with a configured scoresheet gets a ScoresheetInstance seeded automatically.

Application custom field persistence (per UI anchor)

Same file — ExtractCustomFieldsForWorksheet(dto.CustomFields, worksheetId) splits incoming field values per worksheet; PublishCustomFieldUpdatesAsync(applicationId, uiAnchor, customFieldDto) publishes PersistWorksheetIntanceValuesEto. Invoked once per UI anchor, so a single GrantApplication can carry several independent worksheet instances — one per tab/section of the detail UI. Both a legacy single WorksheetId field and a newer WorksheetIds list are supported for backward compatibility.

Assessment → Scoresheet scoring

Worth knowing before you touch this code.

Inconsistent

Most duplicate-name guards throw a plain UserFriendlyException with a hardcoded English string; only Scoresheet.UpdateSectionName uses the namespaced, localizable BusinessException(ErrorConsts.DuplicateSectionName) pattern the rest of the codebase favors.

Tech debt

Unused

By design

By design

No unique DB indexes beyond primary keys — duplicate-name prevention (section names, field names) is an in-memory aggregate rule only, never DB-enforced.

Roadmap: permission-aware definitions

STATUS — ASPIRATIONAL, NOT STARTED. Dashed lines and borders on this page mark proposed, not-yet-built ideas.

Today, Flex has no permission model of its own (§10). A worksheet or scoresheet is visible to anyone who can see its UI anchor's tab, gated only by two coarse, all-or-nothing switches — the host page's builder permission, and the Unity.Flex tenant feature flag. The grand vision is to make permission-awareness a first-class part of the definition itself: a program admin building a worksheet could attach a permission requirement directly to a section or field — the same way they already set its type, label, or required-ness — and have rendering widgets and app services respect it automatically.

This isn't a green-field problem

Two pieces of prior art already in this codebase solve adjacent problems, and are the natural starting point rather than inventing a parallel mechanism.

ABP permissionsused everywhere else in this codebase

Every other module gates access through [Authorize(PermissionName)] on app services and IPermissionChecker.IsGrantedAsync(permissionName), with permissions declared in a *PermissionDefinitionProvider. Flex is the odd one out — no FlexPermissionDefinitionProvider exists anywhere in the module.

The Zone systemUnity.GrantManager.Domain/Zones, Web/TagHelpers/Zone

The host app already solves a close cousin of this problem for its own hardcoded UI. The Application Details page is built from named tabs and zones, each toggleable per form by an admin (ZoneManager, ZoneManagementAppService, stored as a JSON ZoneGroupDefinition setting). A <zone>/<zone-fieldset> Razor tag helper gates rendering with three layered, independent checks — see below.

The Zone tag helper's three-layer check

CheckSourceAnswers
FeatureIFeatureChecker.IsEnabledAsync(FeatureRequirement)Is this capability on for the tenant at all?
Zone toggleIZoneChecker.IsEnabledAsync(ZoneRequirement, formId)Has an admin enabled this tab/zone for this form?
PermissionIPermissionChecker.IsGrantedAsync(PermissionRequirement)Does this user have the ABP permission to see it?

ZoneRequirementType (Full, ToggleOnly, PermissionOnly) lets a zone opt out of the toggle or permission check independently. The tag helper also separates read from update: a <zone-fieldset> renders disabled when UpdatePermissionRequirement fails even though PermissionRequirement (read) passed — a visible-but-locked state. This is exactly the shape of problem Flex will eventually have, solved once already in this codebase.

What "leveraging the zone system" could mean

Roughly in order of how much new machinery each requires — listed to show the range, not to pick a winner.

1

Copy the pattern, not the code. Give WorksheetSection/CustomField (and the scoresheet equivalents) optional ReadPermission/UpdatePermission properties, and have the runtime widgets run the same three-layer check inline via IPermissionChecker. Lowest coupling, but duplicates the Zone logic.

2

Register Flex sections as real zones. Each published WorksheetSection registers an entry in the form's ZoneGroupDefinition, so the existing ZoneManagementAppService admin screen and <zone> tag helper drive Flex visibility too — one governance surface instead of two. Requires bridging Flex's per-instance correlation model with the Zone system's per-form model.

3

Make the Zone system correlation-aware. Extend IZoneChecker/ZoneManager to scope by (correlationId, correlationProvider) the way WorksheetInstance already does, rather than only by form id — letting one mechanism cover both the host's hardcoded tabs and Flex's dynamic content.

A head start that already exists: SecurityClassification

Worth flagging before the open questions below, because it changes the shape of the problem: every field definition already carries a SecurityClassification property (ProtectedA/B/C, mirroring the real BC Government classification standard), and the builder already has a UI for setting it, complete with explanatory tooltips — see §05. It is currently presentation metadata only, read by nothing. This is precisely the "sensitivity tier" concept the first open question below reasons toward from scratch — except it doesn't need to be designed, it needs to be wired up: a real enforcement layer is the missing piece, not the tiering concept itself.

Open design questions

Open

Static permissions vs. runtime-created definitions. ABP permissions are declared at compile time; worksheets/sections/fields are created at runtime by an admin. "One ABP permission per field" doesn't fit that model. The existing SecurityClassification tiers are the natural fit: map each of ProtectedA/B/C (plus "none") to a real, statically-declared ABP permission, and enforcement becomes "does this user hold the permission for this field's tier" rather than minting a permission per field.

Open

Server-side enforcement, not just UI hiding. Per this codebase's own security rules: never rely solely on UI-level permission hiding. Whatever gets attached to a definition must also be checked in the app services that read/write instance data — not only in the rendering widgets — or the API stays an unguarded backdoor around a UI-only restriction.

Open

Read/write split. Mirror the Zone tag helper's read vs. update distinction — a field being visible to a role doesn't mean that role can edit it.

Open

Backward compatibility. Every worksheet/scoresheet published today has nothing attached to any section or field. Absent-permission must keep meaning "visible/editable to anyone with existing host-level access" — additive, not a breaking migration.

Open

Admin UX. The builder screens need a permission (or sensitivity-tier) picker per section/field. Exposing the full ABP permission tree would be overwhelming; a curated, Flex-scoped list is likely necessary.

Open

Reporting implications. The reporting pipeline currently flattens all answers/values uniformly. A permission-gated field needs a story for whether restricted data flows into shared reports at all — downstream of Unity.Reporting and Metabase, not just the Flex UI.

Suggested next step

Before writing code: a short spike comparing option 1 against option 2 against a small number of real worksheets/scoresheets in use today, to see whether form-level granularity (what Zones give today) is actually sufficient, or whether section/field-level granularity is a hard requirement. That answer determines which option is worth pursuing.
