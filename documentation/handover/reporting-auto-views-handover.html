Auto-Generated Views

The reporting path that came first: publish a worksheet, a scoresheet, or sync a CHEFS form version, and a database view appears — no configuration, no owner, every column TEXT. It works, it is still in production, and it is being retired. This page is the complete account of what it does and how to take it out in two phases without breaking a single Metabase report before the reporting team is ready.

01

The pattern

Three steps, all automatic, none of them involving a decision by a person.

On publish
ReportKeys | ReportColumns definition flattened to two pipe-delimited lists
On save / intake
ReportData (jsonb) instance answers flattened to { key: value }
Immediately after
generate_*s_view(id) one TEXT column per key, reading ReportData

Every entry point is gated on the per-tenant Unity.Reporting feature (FeatureConsts.Reporting). Nothing here runs for a tenant without it.

Telling the two paths apart in a database

-- explicit views are exactly the ViewName values in the config table SELECT "ViewName" FROM "Reporting"."ReportColumnsMaps"; -- everything else under Reporting is an auto view (or an orphan) SELECT viewname FROM pg_views WHERE schemaname = 'Reporting' AND (viewname LIKE 'Form-%' OR viewname LIKE 'Worksheet-%' OR viewname LIKE 'Scoresheet-%');

The naming conventions are the tell: auto views are Form-…, Worksheet-…, Scoresheet-…, mixed-case with hyphens. Explicit views are lowercase with underscores.

Persisted state

Six columns of configuration across three definition tables, and three JSONB snapshot columns across three instance tables. This is exactly what Phase 2 removes.

ReportKeys and ReportColumns are two parallel |-delimited lists (ReportingConsts.ReportFieldDelimiter). Index i of one is the JSON lookup key; index i of the other is the resulting SQL identifier. On the Flex side the contract is IReportableEntity<T> with its SetReportingFields(keys, columns, viewName) method.

From AvailableChefsFields. Types simplebuttonadvanced, datagrid, and hidden are excluded outright; simplecheckboxes and simplecheckboxadvanced expand to one key per option value. Columns are the same keys truncated at 63 characters.

Per field via ReportingFieldsGeneratorFactory — CheckboxGroupReportingFieldsGenerator and DataGridReportingFieldsGenerator expand into several keys; everything else goes through the default generator.

The generators seed the dictionary with every report key mapped to null and then overwrite the ones that have values, so the JSON shape stays stable across instances. The scoresheet generator additionally writes a TotalScore entry. Both Flex generators swallow every exception and log — report data never blocks intake or assessment, which is also why it can silently drift.

05

Sync tooling

Because generation fails silently, three IT-Admin services exist to repair the drift. No UI — they are reachable only through ABP's auto-generated API. Each takes an optional tenantId and otherwise loops every tenant, re-checking the Unity.Reporting feature per tenant.

FormsReportSyncServiceAppServiceSyncFormVersionFields · SyncFormSubmissionData

Form versions with an empty ReportViewName; submissions whose ReportData is empty or {}, processed 25 at a time in their own units of work. Its GenerateFormVersionFields already carries a // Deprecated - to be removed once new reporting is fully rolled out comment.

WorksheetReportingFieldsSyncAppServiceSyncFields · SyncData

Published worksheets with an empty ReportViewName; ReportData for every worksheet instance, unconditionally.

ScoresheetReportingFieldsSyncAppServiceSyncQuestions · SyncAnswers

The scoresheet equivalent.

All three are [Authorize(IdentityConsts.ITAdminPolicyName)]. All three disappear in Phase 1.

06

Why it is going away

These are structural, not incidental. Each one is already solved on the explicit path.

Real risk

View names are not valid bare identifiers. ReportColumnsMapRepository.IsValidPostgreSqlIdentifier accepts only ^[a-zA-Z_][a-zA-Z0-9_]*$, and AssignRoleToAllViewsAsync validates every name it reads back from pg_views before interpolating it into a GRANT. Hyphenated auto view names fail that check, so "assign role to all views" throws part-way through and leaves the rest of the schema ungranted. This is the one rough edge that actively damages the other path.

Real risk

Column names are truncated but not de-duplicated. Keys are cut at 63 characters with nothing done about collisions — two long CHEFS keys sharing a 63-character prefix produce two identically named columns and the CREATE VIEW fails outright.

Latent

Unqualified DROP VIEW. The drop resolves through search_path while the create is explicitly "Reporting".%I. If Reporting is not on the search path, the drop silently misses and the create then fails on the existing view.

Design

Everything is TEXT. Numbers, dates, currency, booleans all arrive as strings, so every Metabase model has to cast. The explicit path emits real NUMERIC / DECIMAL(18,2) / TIMESTAMP / BOOLEAN via the safe_to_* helpers.

Design

Failures are silent. All three handlers catch Exception and log; only the submissions handler notifies Teams. There is no ViewStatus equivalent and nothing surfaces in the UI, so a tenant can sit with a stale or missing view indefinitely — which is why §05 exists at all.

Design

Form-version views never refresh. The ReportViewName-empty guard means a re-synced CHEFS schema does not update ReportKeys, so fields added to a form version never appear in its view.

Design

ReportData is a second copy of the answers. It duplicates data already in Submission, WorksheetInstances.CurrentValue, and Flex.Answers, and drifts from them whenever generation fails.

Missing

No cross-version story. One view per form version means a multi-version report is assembled by hand in Metabase. The *_consolidated providers exist precisely to solve this.

Phase 1 — stop generating

Goal: no new auto views, no new Report* values. Existing views and columns stay exactly where they are, so every current Metabase report keeps working untouched. This phase is blocked on nothing and can ship immediately.

1.3

Untangle the AI scoresheet contract

coupled

FormScoresheetOperationExecutor reads and round-trips ReportColumns, ReportKeys, and ReportViewName through the AI payload, and AIProviderPayloadValidator requires all three to be present on a scoresheet payload. FormScoresheetResponse and the seeded prompt in AIPromptDataSeeder carry them too.

Either keep passing empty strings through, or — better — strip the three properties from the AI contract, the validator, the response DTO, and the seeded prompt together. Changing the seeded prompt affects tenants that already hold prompt rows, so plan a data update alongside the code change.

1.4

Trim the DTOs, keep the columns

code

Drop the three properties from CreateWorksheetDto, WorksheetDto, ApplicationFormVersionDto, and the two Mapperly profiles — nothing in the Razor pages or JavaScript reads them (verified by search).

Leave the database columns and the entity properties in place. With IReportableEntity<T> gone, SetReportingFields disappears and the columns become plain persisted state, frozen at their last generated values. That is deliberate: it keeps every existing view queryable while the reporting team migrates.

1.5

Verify

test

On a tenant with the Unity.Reporting feature enabled: publish a worksheet, publish a scoresheet, and re-sync a CHEFS form version. Then confirm no new ReportKeys/ReportViewName values were written, pg_views under Reporting is unchanged before and after, and no generate_*s_view call appears in the logs.

Phase 1 drops no views, no columns, and no stored procedures. It is fully reversible by reverting the commit.

08

Phase 2 — remove the data

Hard gate

Do not start until the reporting team confirms in writing that no Metabase model, question, or dashboard — and no external consumer — references any Form-*, Worksheet-*, or Scoresheet-* view. Inventory them per tenant with the queries in §01 first, and take a database backup: DROP COLUMN on ReportData is irreversible.

Prerequisite already verified

None of get_formversion_data, get_consolidated_formversion_data, get_worksheet_data, get_consolidated_worksheet_data, or get_scoresheet_data reads ReportData, ReportKeys, ReportColumns, or ReportViewName. They read source data directly:

formversion · consolidated
public."ApplicationFormSubmissions"."Submission"
worksheet · consolidated
Flex."WorksheetInstances"."CurrentValue" joined to Flex."Worksheets"
scoresheet
Flex."ScoresheetInstances" → Assessments → Applications; values from Flex."Answers"; total from calculate_scoresheet_total_score

So dropping these columns cannot break an explicitly configured view.

One tenant migration, in this order

2.1

Drop the auto views

Generated names are not predictable from the migration alone, so drop them by pattern in a DO block iterating the pg_views list from §01, using EXECUTE format('DROP VIEW IF EXISTS %I.%I', ...).

2.2

Drop the stored procedures

DROP PROCEDURE IF EXISTS "Reporting".generate_submissions_view(uuid); DROP PROCEDURE IF EXISTS "Reporting".generate_worksheets_view(uuid); DROP PROCEDURE IF EXISTS "Reporting".generate_scoresheets_view(uuid);

Then delete the three Scripts/*.sql files, their <EmbeddedResource> entries in Unity.GrantManager.EntityFrameworkCore.csproj, and their RunEmbeddedScript lines in 20260721203242_Initial.cs.

2.3

Drop the definition columns

ALTER TABLE "Flex"."Worksheets" DROP COLUMN "ReportKeys", DROP COLUMN "ReportColumns", DROP COLUMN "ReportViewName"; ALTER TABLE "Flex"."Scoresheets" DROP COLUMN "ReportKeys", DROP COLUMN "ReportColumns", DROP COLUMN "ReportViewName"; ALTER TABLE public."ApplicationFormVersion" DROP COLUMN "ReportKeys", DROP COLUMN "ReportColumns", DROP COLUMN "ReportViewName";

Remove the matching properties from Worksheet, Scoresheet, and ApplicationFormVersion.

2.4

Drop the instance data columns

irreversible
ALTER TABLE "Flex"."WorksheetInstances" DROP COLUMN "ReportData"; ALTER TABLE "Flex"."ScoresheetInstances" DROP COLUMN "ReportData"; ALTER TABLE public."ApplicationFormSubmissions" DROP COLUMN "ReportData";

Remove WorksheetInstance.ReportData + SetReportingData, ScoresheetInstance.ReportData + SetReportingData, ApplicationFormSubmission.ReportData, CreateWorksheetInstanceDto.ReportData, and WorksheetInstanceReportDto. DataGridWriteService.GenerateReportDataForNewRowAsync in Unity.Flex.Web also writes ReportData for new data-grid rows and goes with them.

ScoresheetInstances.ReportData also carries the TotalScore entry the auto scoresheet view exposes. The explicit path computes the total independently from Flex.Answers via calculate_scoresheet_total_score, so no scoring capability is lost — but confirm nothing else reads ReportData->>'TotalScore' before dropping.

2.5

Regenerate and verify

Add the migration against the tenant context explicitly (--context GrantTenantDbContext --output-dir Migrations/TenantMigrations).

After it runs, SELECT viewname FROM pg_views WHERE schemaname = 'Reporting' should return exactly the ViewName set from Reporting."ReportColumnsMaps". Then run "assign role to all views" for the tenant — with no hyphenated names left it should complete without throwing, closing the cross-path rough edge in §06.
