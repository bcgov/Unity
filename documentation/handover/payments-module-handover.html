Unity.Payments

A grant is only real when the money moves. This module turns an approved application into a payment request, walks it up a three-level expense-approval ladder where the state machine is also the permission gate, and then either posts an AP invoice to CAS or hands the batch to Financial Services Branch as a spreadsheet. This page is the complete reference: the ladder, the CAS loop, the supplier mirror, and the rough edges.

01

The shape of a payment

Once an application is GRANT_APPROVED with an approved amount, staff decide how much of that envelope to pay now, the amount is signed off one to three times, and only then does anything leave Unity. Approving the last level never calls CAS on the request thread — it enqueues.

01 · Request
PaymentRequestAppService.CreateAsync batch name, reference no, L1 + L2 approval slots
02 · Approve
PaymentsManager.TriggerAction Stateless machine · permission-guarded transitions
03 · Settle
InvoiceConsumer → CAS or FSB spreadsheet when the form prevents payment

How much is left to pay

The default amount on a new payment is the remaining amount, and grants are frequently paid in instalments across a parent/child application hierarchy that shares one envelope. PaymentRequestPageHelperService.GetRemainingAmountAsync computes it as:

remaining = ApprovedAmount − Σ payments on this application − Σ payments on every linked child application where "payments" excludes L1/L2/L3-declined, Cancelled, and anything whose CAS InvoiceStatus is Cancelled, NotFound or Error

A parent/child group gets one shared ceiling stamped onto every row, and the whole calculation is redone server-side on POST — so a form left open while someone else spends the envelope cannot over-commit it.

Identity of a payment

Every payment created in one submission shares a batch. The numbers are generated per batch from the tenant's PaymentIdPrefix and a per-year sequence:

BatchName {prefix}_UNITY_BATCH_{max(BatchNumber) + 1} ReferenceNumber {prefix}-{year}-{seq:D4} ← unique index; the UI's "Payment ID" InvoiceNumber {prefix}-{year}-{applicationRefNo}-{seq:D4} ← what CAS sees

Two entry points that skip the ladder entirely

Historical paymentsCreateHistoricalAsync

Money paid before Unity, recorded so history and rollups are complete. Constructed straight into HistoricalPayment with InvoiceStatus and PaymentStatus both "Paid", and no expense approvals at all. Never sent to CAS. The only transition available is Cancel.

FSB routeform.PreventPayment

Programs not permitted to submit directly to CAS run the same ladder, but the final Submit lands on FSB with InvoiceStatus = SentToAccountsPayable instead of queueing an invoice. The batch is emailed to Financial Services Branch as an .xlsx — see §06.

The UI sends no trigger

The approval modal posts { PaymentRequestId, IsApprove, Note } per payment. DetermineTriggerActionAsync works out which trigger applies from the payment's current status and the caller's own permissions — which is why a user holding several approval permissions always acts at the lowest level the payment is sitting at:

has L1 permission and status ∈ {L1Pending, L1Declined} → IsApprove ? L1Approve : L1Decline has L2 permission and status ∈ {L2Pending, L2Declined} → !IsApprove → L2Decline amount > threshold → L2Approve (routes to L3) otherwise → Submit (skips L3) has L3 permission and status ∈ {L3Pending, L3Declined} → IsApprove ? Submit : L3Decline otherwise → None — payment silently skipped

Separation of duties · AB#26693

The same person may not approve at L1 and then again at L2. UpdateStatusAsync enforces it twice: once up front across the whole batch — if any payment being approved is in L2Pending with the current user as its Level 1 decision-maker, the entire call throws before anything changes — and again per payment inside CanPerformLevel2ActionAsync. The modal also carries PreviousL1Approver so affected rows can be flagged before submitting.

The Level 3 slot does not exist until it has to

Payments are created with Level 1 and Level 2 approval rows only. The Level 3 row is inserted — or deleted — by the approval modal's page model while it renders, based on whether the amount crosses the threshold. That write happens during a GET; see §08.

The machine gates, the ladder decides

TriggerAction runs the workflow against a local copy of the status purely to validate the transition, then computes the real destination with a separate if/else ladder and applies that to the entity. Submit is where the two most visibly differ — the machine always says Submitted, the ladder may choose FSB:

bool preventPayment = await GetFormPreventPaymentStatusByApplicationId(paymentRequest.CorrelationId); if (preventPayment) { statusChangedTo = FSB; paymentRequest.SetInvoiceStatus(SentToAccountsPayable); } else { statusChangedTo = Submitted; await casPaymentRequestCoordinator.AddPaymentRequestsToInvoiceQueue(paymentRequest); }

Cancellation

Eligible only from HistoricalPayment, L1Pending, L2Pending and L3Pending — a payment already submitted to CAS cannot be cancelled in Unity. Cancelling stamps CancelledOn, CancelledById and CancelledBy, and for a historical payment additionally sets InvoiceStatus = Cancelled and PaymentStatus = "Not Paid" so the rollup stops counting it as paid.

03

Domain model & schema

Every entity implements IMultiTenant; ABP's automatic filter does the isolation and nothing in this module filters TenantId by hand. The tables live in the Payments schema of the per-tenant database, with an empty table prefix.

The layout is not like the other modules

There are no .Domain, .Domain.Shared or .EntityFrameworkCore projects. The domain model lives in Unity.Payments.Application/Domain/ and persistence in Unity.Payments.Application/EntityFrameworkCore/, so nothing structurally stops a domain type depending on an application service — and InvoiceManager, a DomainService, already injects PaymentConfigurationAppService directly.

Shared localization (PaymentsResource), PaymentsPermissions, HtmlTable ↑ Application.Contracts DTOs, I*AppService, enums, CAS wire types, CasPaymentRequestStatus codes ↑ Application Domain/ · EntityFrameworkCore/ · Integrations/ · PaymentRequests/ Suppliers/ · PaymentTags/ · Handlers/ · Permissions/ ── references Unity.GrantManager AND Unity.Notifications ── ↑ Web Razor Pages, PaymentInfo / SupplierInfo / PaymentActionBar widgets

The coupling runs both ways: this module references host types (IApplicationRepository, IApplicationLinksService, IEndpointManagementAppService) and the host references payments types (PaymentThreshold, AccountCoding, IPaymentRequestAppService, PaymentGroup). Payments and the core GrantManager application are mutually coupled, not cleanly separable.

Two DbContexts over the same tables

PaymentsDbContext is real and registered, its connection-string name is "Tenant", and the module's custom repositories derive from it. GrantTenantDbContext also calls ConfigurePayments() — and that is the context migrations come from. The module ships none of its own; schema changes are added as tenant migrations.

Core entities

PaymentRequestFullAuditedAggregateRoot<Guid>

The aggregate root. Amount, payee/supplier/site snapshot, batch, Status, the CAS response fields, expense approvals, tags, note, FSB tracking, cancellation tracking. State changes only through fluent Set* methods. IsApproved is computed as all approvals approved — which is vacuously true for a historical payment, since it has none.

ExpenseApproval

One approval slot: Type (Level1/2/3) and Status (Requested/Approved/Declined). DecisionUserId and DecisionDate are write-once — the setters throw once set, and a test asserts it on purpose. That is deliberate, and it is also what breaks re-approval after a decline (§08).

Supplier+ Site

A mirror of CAS master data. CAS addresses a payment by supplier number plus site code, so both are required. Supplier updates go through value objects (SupplierBasicInfo, ProviderInfo, SupplierStatus, CasMetadata, MailingAddress); Site exposes public setters and two static comparison helpers used by the sync path.

AccountCoding

Five GL segments with exact lengths enforced on create and update — MinistryClient 3, Responsibility 5, ServiceLine 5, Stob 4, ProjectNumber 7, the last three alphanumeric-only. Formatted for CAS with a fixed postfix.

039.15006.10120.5185.1500000.000000.0000
PaymentConfiguration

The tenant's PaymentIdPrefix and default account coding. One row per tenant in practice — every read takes GetListAsync()[0] or FirstOrDefaultAsync(), and nothing enforces the cardinality.

PaymentThreshold

UserId → Threshold. Rows are created lazily by the host when the L2-approver settings screen is opened, so a user who has never appeared there has no row and contributes no threshold.

PaymentTag

A join between a payment and the host's global Tag — the same tag table the applications list uses, which is why ConfigurePayments() re-declares the host's Tag mapping so the FK resolves from either context.

Two status families, moving independently

Status is Unity's state. InvoiceStatus and PaymentStatus are CAS's, stored as free strings from a constants class, not an enum. A payment is routinely Submitted in Unity and Never Validated in CAS at the same time.

04

The CAS loop

CAS is the province's Corporate Accounting System. Unity uses its ORDS REST API for invoices, invoice status, and supplier master data. The base URL is a DynamicUrl row (PAYMENT_API_BASE) resolved through the host's IEndpointManagementAppService — configuration in data, not a constant.

Authentication is per tenant

casClientCode = tenant.ExtraProperties["CasClientCode"] → UserFriendlyException if absent casClientId = ICasClientCodeLookupService.GetClientIdByCasClientCodeAsync(casClientCode) clientSecret = configuration["CAS_API_KEY_{CASCLIENTCODE}"] token = POST {casBaseUrl}/oauth/token → cached in IDistributedCache<TokenValidationResponse, string>

The tenant's CasClientCode is set through Tenant Management. A tenant without one cannot pay — the token service throws before any request is made.

Invoice creation

EnqueueCasPaymentRequestCoordinator

An InvoiceMessages envelope with a 10-minute TTL, carrying the payment id, invoice number, supplier number, site number and tenant id. Exceptions here are caught and logged — a broker outage does not roll back the approval, but it does leave the payment at Submitted with nothing scheduled to retry it (§08).

ConsumeInvoiceConsumer

Tenant context and audit scope are established by the shared QueueConsumerHandler before ConsumeAsync runs, so the consumer only guards against empty invoice numbers and empty tenant ids.

Build & POSTInvoiceService

POST {base}/cfs/apinvoice/. Returns null and silently skips the send when the site, its supplier, the supplier number, or the account distribution code is missing.

payGroup: GEN EFT | GEN CHQdates: dd-MMM-yyyy, Pacificone invoice line, full amount
RecordInvoiceManager

Three attempts, each in a fresh unit of work, catching concurrency exceptions with a 75 ms pause. Skips early if InvoiceStatus is already SentToCas — the idempotency guard against a double-consume. Writes SentToCas or Error plus the HTTP status and response body.

Invoice dates are computed in Pacific time, not UTC, and deliberately so — the code carries the comment that CAS rejects future-dated invoices. PaymentAdviceComments is the payment description capped at 50 characters, falling back to "{TenantName} - Grant Payment"; QualifiedReceiver is the Level 1 approver's name capped at 150.

Reconciliation

A nightly [DisallowConcurrentExecution] Quartz worker sweeps every tenant and enqueues a re-check for each payment in a re-check status. Staff can also trigger it for selected rows with Check Status on the list page — same message, same consumer.

ServiceUnavailable SentToCas NotFound SentToAccountsPayable Never Validated

Those are the five InvoiceStatus values that put a payment back in the queue. Note SentToAccountsPayable is among them — FSB payments are polled against CAS nightly and will keep returning NotFound until Financial Services Branch keys them in.

The consumer GETs cfs/apinvoice/{invoiceNumber}/{supplierNumber}/{siteNumber} and, if any invoice status came back, writes status, payment status, payment number and date onto the payment inside its own transactional unit of work. Two quirks: a failed-but-answered response stamps the HTTP status code string into InvoiceStatus (that is where ServiceUnavailable comes from), and a payment already at NotFound that comes back NotFound again is rewritten to the literal "NotFound2" — a human signal, read by nothing.

How failures surface

ApplyErrorSummary copies CasResponse into the DTO whenever it is present and not "SUCCEEDED", which renders as a clickable CAS Response cell opening the full text. Separately, anything at ServiceUnavailable or Error modified in the last 24 hours goes into the nightly failure summary email — see §06.

05

Suppliers & sites

Unity never invents a payee. Supplier and site rows are a mirror of CAS, refreshed opportunistically whenever staff touch supplier information — including a live comparison on every render of the supplier widget's site list.

SupplierService GET cfs/supplier/{number} or cfs/supplier/{bn9}/businessnumber ↓ publishes UpsertSupplierEto (local event bus) UpsertSupplierHandler upsert Supplier · dedupe + upsert Sites · resolve default PaymentGroup ↓ publishes ApplicantSupplierEto SupplierCreatedHandler link supplier to applicant · delete or tombstone sites CAS dropped (host)

What the sync protects

Bank accounts are maskedat the parse boundary

GetSiteEto stores ****1234 — all but the last four characters replaced. The unmasked account number never enters the Unity database.

Empty supplier number rejected

A CAS response with a blank suppliernumber raises UserFriendlyException rather than creating a nameless payee.

Duplicates collapsed twice

Incoming site ETOs are deduplicated by site code because CAS can return duplicates, and SiteAppService.InsertAsync independently checks for an existing site with the same number under the same supplier and updates instead.

No-op writes skipped

Site.SiteMatchesSiteDto compares every field; an unchanged site is not written at all, so the audit trail is not filled with empty updates.

Referenced sites are tombstoned, not deletedMarkDeletedInUse

When CAS stops returning a site, the host checks whether any application uses it as DefaultSiteId or any payment references it. If so the site is flagged rather than removed, and a later CAS refresh that returns it again clears the flag.

Default site and pay group

The default site lives on the application, not the applicant — different applications from the same applicant can be paid to different sites. A payment cannot be created without one. Pay group has three inputs: the application form's DefaultPaymentGroup when a site is created, a manual override from the widget, and any CAS refresh, which rewrites the site wholesale.

Clearing an applicant's supplier cascades: ClearApplicantSupplierAsync nulls Applicant.SupplierId and then clears DefaultSiteId on every one of that applicant's applications, because those sites belonged to the supplier being unlinked.

An EFT site with no bank account blocks payment creation — the create modal reports it as a row-level error and disables the fields.

06

FSB & failure email

Payments never talks to CHES. It publishes an EmailNotificationEvent on the local event bus and the Notifications module owns everything after that. Two kinds of message originate here, plus a status event the host can turn into a third.

SendFsbNotification
Fired when payments enter FSB during an approval batch. One email per batch name, subject is the batch name, with a 20-column .xlsx attached. Recipients: the FSB-AP email group.
SendFailedSummary
Nightly, per tenant. An HTML table of payments that failed at CAS in the last 24 hours. Recipients: the union of every registered IEmailRecipientStrategy — currently the Payments email group.
PaymentStatusChangedEvent
Published on create, on any real status change, and on cancel. The host's ScheduledNotificationEventHandler may match it to a configured notification and email the applicant. Payments neither knows nor cares whether one exists.

Two strategies, one of which hides from the interface

PaymentsEmailGroupStrategy implements IEmailRecipientStrategy and is registered as a singleton, so it is picked up by the IEnumerable<IEmailRecipientStrategy> injection the failure summary uses. FsbApEmailGroupStrategy is the same shape but deliberately does not implement the interface — its own comment says so — precisely so the FSB-AP group is never swept into unrelated notifications.

Both resolve group → members → identity emails, and treat a missing group, an empty group, or a member without an address as a logged warning that simply yields fewer recipients. No recipients means no email is sent at all, and only a warning records it.

The round trip that stamps the payment

A payment is only marked as notified once CHES actually accepted the message — not when the email was queued:

FsbPaymentNotifier ──▶ EmailNotificationEvent (SendFsbNotification) ↓ EmailNotificationHandler writes EmailLog, uploads the xlsx to S3, stores payment ids on EmailLog.PaymentRequestIds ↓ RabbitMQ → EmailConsumer → CHES ↓ only on a success status code FsbEmailSentEto { EmailLogId, PaymentRequestIds, SentDate, TenantId } ↓ FsbEmailSentEventHandler SetFsbNotificationEmailLog(...) → FsbApNotified = "Yes"

FsbApNotified is a column on the Payments list, so staff can see at a glance which FSB payments have genuinely reached AP.

Resilience is deliberate here

An email failure must never undo an approval. The notifier call in UpdateStatusAsync is wrapped and its exceptions logged and dropped; inside the notifier, a failure on one batch is logged and the remaining batches still send; inside a batch, a row that throws while being assembled is skipped, and only a batch that yields no rows is abandoned. Approver and requester names are resolved with a single batched identity query per batch, not one per row.

Features, permissions & UI

One feature, off by default

Unity.Payments gates the module four ways: [RequiresFeature] on every app service, a check in the menu contributor, an empty view model from both widgets, and .RequireFeatures(...) on every granular permission.

The Payments list

A ~1,400-line DataTable and the module's main screen. Three things about it are worth knowing before you change it:

requestedFieldsthe client shapes the query

The visible column list is sent with the request, and the query manager uses it to decide what to Include and what to hydrate — site, account coding, tags, expense approvals, requester and applicant details are each loaded only if a column asks for them. An empty list means include everything.

Date-bounded by defaultlast 6 months

The quick-range selection persists in localStorage and is converted from Vancouver local dates to a UTC range, with the "to" date extended to the end of the local day. With no server-side paging (§08), this filter is the only thing bounding the query.

Selections travel by cache key5-minute TTL

Payment ids would blow the URL length limit, so bulk actions write the id list to the distributed cache under BulkAction:PaymentRequestIds:{guid} and open the modal with the key. An expired key produces "The session has expired. Please select payment requests and try again."

Toolbar: Check Status, Approve, Decline, Cancel (permission-gated, exactly one row, with a confirm), History, Filter, saved views, and CSV export. Users can save named views; Reset to Default View restores the default columns, sort, filters and date range.

08

Known rough edges

This module moves money, so the ordering below is by real-world risk rather than tidiness. The first item is a genuine defect; several others are behaviours that are correct but surprising.

Real risk

Re-approving a declined payment throws, and the exception is swallowed. The state machine permits L1Declined → L1Approve → L2Pending, but ExpenseApproval.DecisionUserId is write-once and declining already stamped it. The later .Approve() throws InvalidOperationException, the batch loop catches and logs it, and the payment silently stays declined — simply absent from the returned list. Either the transition should not be offered, or the entity needs an explicit reset.

Real risk

Batch and sequence numbers are racy. GetBatchSetupAsync reads the max batch number and next sequence, then assigns seq + i across the loop. Two concurrent submissions read the same values. The unique index on ReferenceNumber turns the collision into an insert failure rather than a duplicate — but it surfaces as a rethrown exception mid-batch, with earlier payments already inserted.

Real risk

Enqueue failures are silent and unrecoverable. AddPaymentRequestsToInvoiceQueue catches and logs everything. A broker outage leaves the payment at Submitted with no InvoiceStatus — and reconciliation only picks up payments that already have a re-check status, so nothing will ever retry it.

Performance

GetListAsync does no server-side paging. MaxMaxResultCount is set to int.MaxValue, skip and take are ignored, the count query is commented out, and the total is the length of the materialised list. Only the six-month default date filter bounds it — and the user can widen that.

Performance

Both number generators load the whole table. GetMaxBatchNumberAsync materialises every payment request to compute a max; GetNextSequenceNumberAsync does the same, then filters to the current year in memory and parses a sequence out of the most recent reference number. Both are O(n) on a table that only grows, and both run on every payment creation.

Silent

Per-payment exceptions vanish in batch updates. UpdateStatusAsync wraps each payment in a catch-and-log. A payment that fails to transition is omitted from the result with no error shown — the modal reports success for the ones that worked. This is what hides the first item on this list.

Surprising

The approval modal writes to the database during a GET. UpdateExpenseApprovalsAsync inserts or deletes the Level 3 approval row while rendering, so opening and closing the modal without approving anything mutates the payment. The threshold decision it makes there is also re-derived independently when the approval is actually submitted.

Confirm intent

Global exception details are enabled from this module. PaymentsApplicationModule sets SendExceptionsDetailsToClients = true. AbpExceptionHandlingOptions is application-wide, not per-module, so this affects every endpoint in the product.

Confirm intent

Two anonymous page conventions. AllowAnonymousToPage("/Payments/Index") is inert — no such page exists in this module. AllowAnonymousToPage("/PaymentConfigurations/Index") is not: that page reads the tenant payment configuration with no authorization attribute of its own, relying on the ConfigurePayments check on the screen that links to it.

Architecture

The machine validates but does not decide. TriggerAction uses the state machine only as a gate, then computes the destination with a parallel if/else ladder. The two can drift. ConfigureWorkflow also calls Configure more than once for L1Pending, L2Pending and L2Declined, spreading one state's transitions across separate blocks — legal in Stateless, hard to read as a table.

Dead code

PaymentsState, PaymentApprovalSubState, PaymentsAction and the payments copy of FinalDecisionStates are a complete parallel status model that was never adopted. PaymentApprovalAction.L3Approve, Payments.Decline and Payments.EditSupplierInfo are declared and never used. CasClientOptions is bound from configuration and never read. Supplier.SIN is mapped and persisted but never populated from CAS. PaymentRequestDto carries an explicit operator whose body is throw new NotImplementedException().

Naming

PaymentQueueService sits in the Payments module but declares namespace Unity.Notifications.Integrations.RabbitMQ. Domain/UserPaymentThresholds/IPaymentConfigurationRepository.cs declares IPaymentThresholdRepository. The error key …InvalidAccountCodingFiled is misspelled in both the constants and the localization file. The Payments menu item's display name is a hard-coded string, so it does not localize.

Convention drift

The repo's own C# rules require GuidGenerator.Create() and Clock.Now. This module uses Guid.NewGuid() and DateTime.UtcNow throughout — PaymentsManager.CancelPaymentAsync is the lone exception. PaymentRequest.PaymentTags is also explicitly set to null in both public constructors, so the collection is null on a freshly created aggregate.

Coverage

There is no Domain.Tests or EntityFrameworkCore.Tests project. Covered: entity construction, the write-once approval semantics, rollups, repository queries, account coding validation. Untested: the entire state machine, level selection and separation of duties, threshold resolution, the CAS clients and consumers, the supplier sync, the FSB notifier, and parent/child amount validation — which is most of what carries risk.
