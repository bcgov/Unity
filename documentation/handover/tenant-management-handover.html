01

The pattern

Unity Portal is multi-tenant: every ministry/program area is a separate ABP tenant with its own database, users, and feature set. This module creates, provisions, and configures those tenants — from IT Administrators using a direct "New Tenant" form, through IT Operations reviewing and approving Onboarding requests submitted as a specialized CHEFS intake form, to ongoing configuration (connection strings, features, Metabase reporting access, CAS client code, managers).

Whichever door a tenant comes in through, creation converges on exactly one call:

Door A · IT Administrator
CreateModal hand-filled "New Tenant" form
Converges on
TenantAppService.CreateAsync provisioning, connection strings, ETO
Door B · IT Operations
OnboardingRequestAppService .CreateTenantAsync — approved intake form

Neither door is a "lesser" path — Onboarding is a guided front end with an approvable request queue, admin-configurable field mapping, and pre-flight validation layered on top of the identical provisioning logic IT Admins trigger directly. See §06.

02

Module architecture

Unlike Unity.Flex, which owns its entire domain model, EF Core context, and database schema, this module owns no domain layer and no persistence of its own. No Unity.TenantManagement.Domain, no Unity.TenantManagement.EntityFrameworkCore project exists — confirmed by directory listing, not assumed.

Unity.TenantManagement.Application.Contracts → DTOs, app service interfaces ↑ Unity.TenantManagement.Application → AbpTenantManagementDomainModule (ABP's own), Unity.SharedKernel, Unity.Flex.Application.Contracts ZERO reference to Unity.GrantManager — host callbacks via DI only ↑ Unity.TenantManagement.Web → Razor Pages. Reaches into Unity.GrantManager.Application.Contracts and Unity.Reporting.Application.Contracts for UI convenience — the one place the "no host reference" rule relaxes, Web tier only ↑ Unity.TenantManagement.HttpApi / .HttpApi.Client → thin controller/proxy wrappers

Everything domain-specific this module manages is one of: ABP's own built-in Tenant/TenantConnectionString entities, extended purely through flat ExtraProperties — hosted in the host GrantManagerDbContext via [ReplaceDbContext(typeof(ITenantManagementDbContext))] — or host-owned entities it never compiles against (CasClientCode, DynamicUrl, the onboarding-source Application/WorksheetInstance), resolved purely via runtime DI.

The inversion: contracts here, implementations in the host

Unity.GrantManager.Application implements two contracts this module defines but cannot itself fulfil — the same decoupling idea Flex uses for its local-event handlers, just wired through plain DI resolution (LazyServiceProvider.LazyGetService<T>(), degrading gracefully to empty results if nothing is registered) instead of an event bus:

IOnboardingApplicationProvider→ GrantManagerOnboardingApplicationProvider

Reads onboarding request data out of the host's Application/Flex WorksheetInstance tables. See §06.

IOnboardingUserLookup→ CssOnboardingUserLookup

Resolves an email to an IDIR GUID via the host's existing CSS/IDIR directory integration.

Tenant & connection strings

Tenant is Volo.Abp.TenantManagement.Tenant unmodified — no subclass, no [ReplaceDbSetType]. Every domain-specific field is a flat string in Tenant.ExtraProperties (persisted as a single text column, not jsonb).

ExtraProperties keys

Every value here is a deliberate scalar, not a JSON blob — a single JSON-serialized value in one ExtraProperties entry can trip ABP's own Newtonsoft-based change-tracking for that dictionary on the next save (a real, reproducible failure mode). Full detail in §07.

Two connection strings, both encrypted at rest

Also stock ABP (TenantConnectionString, keyed by Name): "Tenant" (full read-write) and "Tenant_Readonly" (independent read-only role, consumed by Metabase — §07). Both AES-256-CBC encrypted via ABP's IStringEncryptionService (PBKDF2/SHA-1, base64), pass phrase from StringEncryption:DefaultPassPhrase.

Encrypt on write

TenantAppService.CreateAsync / UpdateConnectionStringsAsync.

Runtime decrypt

EncryptedTenantConnectionStringResolver — replaces ABP's own resolver via [Dependency(ReplaceServices = true)]; falls back to plain text on decrypt failure.

Migration-time decrypt

EntityFrameworkCoreGrantManagerDbSchemaMigrator.cs.

One-time backfill

TenantConnectionStringEncryptionMigrator.cs, run from GrantManagerDbMigrationService.MigrateAsync() at startup.

Credential generation — TenantConnectionStringBuilder

GenerateCredentialsAsync

Unique T_XXX999 (3 random letters + 3 digits, CSPRNG), checked against currently-existing tenants' LicencePlate only — not orphaned roles from a deleted tenant (§09). Plus a fresh 24-char password.

GeneratePassword

24 chars, A-Za-z0-9 only — quote/backslash excluded at generation, not escaped later, because the password is interpolated into a single-quoted SQL literal by the migrator.

GenerateReadOnlyCredentials

Same DB name, username + "_readonly", a freshly generated, independent password.

Postgres role provisioning

EntityFrameworkCoreGrantManagerDbSchemaMigrator runs synchronously from TenantCreatedEventHandler — before the deferred post-creation sequence is even enqueued, so no race with it. Validates identifiers against an allowlist before interpolating into admin DDL (Postgres identifiers can't be parameterized), then:

DO $$ BEGIN IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = '{roleName}') THEN CREATE ROLE "{roleName}" WITH LOGIN PASSWORD '{password}'; END IF; END $$;

Known gap: the password is only ever set on the CREATE ROLE branch — no ALTER ROLE ... PASSWORD on the "already exists" path. See §09 for the full desync chain this creates.

Permissions & policies

Two Keycloak roles sit above this module's own ABP permissions, defined in modules/Unity.SharedKernel/Permissions/IdentityConsts.cs: ITAdministrator and ITOperations, plus a role-only OR of both, ITAdminOrITOperations.

RoleOrPermissionRequirement — the actual OR logic

None of this module's composite policies (nor the raw Tenants.Create/Update permission names themselves) are gated purely through ABP's normal permission-grant tree. They're registered as custom ASP.NET Core authorization policies in the host: src/Unity.GrantManager.Web/Identity/PolicyRegistrant.cs. Both the raw permission name and its ...OrITOps alias resolve to the identical requirement:

if (requirement.RoleNames.Any(context.User.IsInRole)) { Succeed; return; } if (await _permissionChecker.IsGrantedAsync(context.User, requirement.PermissionName)) { Succeed; }

i.e. succeeds for ITAdministrator OR ITOperations role, OR an individually-granted Tenants.Create ABP permission. Practical effect: IT Operations and IT Administrator can do almost everything gated by these composite policies.

The one deliberate exception

The "New Tenant" modal/button is tightened to IdentityConsts.ITAdminPolicyName alone — a plain role check, no OR — so IT Operations is steered to create tenants only through Onboarding approval instead. Two changes were needed, both scoped to the CreateModal page only (never TenantAppService.CreateAsync itself, which Onboarding still needs unchanged):

  • The toolbar button's AbpPageToolbarOptions.requiredPolicyName.
  • The /TenantManagement/Tenants/CreateModal page's own AuthorizePage convention — closing the "navigate straight to the URL" gap that hiding the button alone would leave open. This codebase's own rule: never rely solely on UI-level permission hiding.

06

Onboarding — tenant creation as a specialized intake form

The single most important thing to understand about Onboarding: there is no OnboardingRequest table. An onboarding request is a Unity.GrantManager Application — the exact same entity behind ordinary grant applications — whose ApplicationForm.Category == "Onboarding". A CHEFS form is authored with that category, submitted through the normal intake pipeline, and the resulting Application plus its Flex WorksheetInstance data is what the Onboarding screens read and act on. Zero new persistence was built — it's the intake/Flex machinery, repurposed wholesale.

Two data sources merged per request

Core fieldsSQL-filterable

Real Application/Applicant/ApplicantAgent columns, enumerated by OnboardingCoreFieldRegistry — a static list of CoreFieldDefinition(Key, Label, Type, EfPath, Selector), filterable/sortable in SQL via System.Linq.Dynamic.Core.

Worksheet fieldsin-memory only

Arbitrary Flex CustomFields on the form's WorksheetInstances, fetched via IWorksheetInstanceAppService and parsed in memory — JSONB can't be filtered/sorted in SQL. An explicit PERF comment flags this as fine at current volume.

Field mapping is admin-configurable, not hardcoded

Which worksheet-field key means "tenant name", "super users", "branch", "features", etc. is stored per-user (falling back to global) via ISettingManager (OnboardingColumnConfigSettings). Different onboarding CHEFS forms — with entirely different field keys — can all feed the same tenant-creation flow, as long as an admin maps the columns once through the UI. No code change per form revision.

Validation steps

Same auto-discovery pattern as post-creation steps (§07): ITransientDependency, Order/StepName/ValidateAsync, run ascending, collected into "[{StepName}] {Issue}" messages. Run by both the client pre-check and the server-authoritative approval — the client result is never trusted alone.

Why IT Operations, specifically

The whole surface — controller, both pages, the app service — is [Authorize(ITOperationsPolicyName)]. This is the flip side of the "New Tenant" button being IT-Administrator-only (§04): IT Operations creates tenants exclusively through this reviewed, validated path; IT Administrators can also use the direct modal. Both converge on the identical TenantAppService.CreateAsync call.

Post-creation provisioning & Metabase

Creating the ABP Tenant row, its Postgres database, and its roles happens synchronously. Everything that depends on an external system — currently, registering the tenant with Metabase for reporting access — happens asynchronously, as a deferred background job sequence.

The step sequence

IPostTenantCreationStep — implement in any module, register ITransientDependency, picked up automatically:

interface IPostTenantCreationStep { int Order { get; } string Key { get; } // stable, machine-readable — must not change once shipped string StepName { get; } // human-readable, used in logs and the status UI bool ContinueOnError { get; } Task<bool> CanExecuteAsync(Guid tenantId) => Task.FromResult(true); Task ExecuteAsync(Guid tenantId); }

PostTenantCreationSequenceJob runs steps one per job execution, ascending Order, self-re-enqueuing for the next index — driven entirely by ABP's background job queue. A step's exception is always caught and logged, never rethrown; ABP's own job retry never engages. ContinueOnError = true logs and moves to the next step; false stops the sequence. Recovery from a failure is currently a manual re-enqueue — no retry button exists yet (§09).

Status tracking — Waiting / Success / Failure / Error

Waiting is seeded for every step at tenant-creation time, so the UI shows something immediately. Success/Error are set after a step returns/throws. Failure is reserved for a future step reporting a handled non-exception failure — unreachable today since the one step either succeeds or throws. A step skipped via CanExecuteAsync returning false stays Waiting, not a terminal result — it may still run on a later manual re-enqueue.

Why flat ExtraProperties, not a JSON blob

Status is stored as one flat scalar key per field — PostCreationStepKeys (comma-separated) plus PostCreationStep_{key}_Name/Status/Message/UpdatedAt per step — matching how every other ExtraProperties entry in this module is a flat string. This matters: Tenant.ExtraProperties round-trips through EF Core via ABP's own Newtonsoft-based change-tracking, and a string value that itself parses as a JSON array makes the next save of that tenant throw Unable to cast object of type 'JArray' to type 'JObject' — a real, reproducible failure mode. Keeping every value a plain scalar avoids it entirely.

The DTO surfaced to the browser is still a JSON array string, but built fresh at read time from the flat fields — never written back into ExtraProperties.

MetabaseApiClient — handling Metabase's API inconsistencies

Metabase's own API is inconsistent enough that the client works around it in three specific ways.

Response shape

Metabase inconsistently wraps list responses ({"data":[...]}) or returns a raw array — including the response body of POST /api/permissions/membership, which the code doesn't even use. Call sites that only need success/failure use PostVoidAsync, which validates the HTTP status without forcing a JObject cast on a body nothing needs.

Racy membership check

AddGroupMemberAsync's check-then-act can race under concurrent/retried registrations; Metabase surfaces a duplicate membership as a raw 500 (unhandled DB unique-constraint violation), not a clean 409. On a POST failure, it re-checks membership — if the user is a member now, by whatever path, that's treated as success.

Transient 422

POST /api/database returns before Metabase finishes asynchronously validating the connection; an immediate sync_schema/rescan_values call can transiently 422 ("Looks like your Password is incorrect") though the connection is fine — and 422 isn't in the HTTP client's auto-retry list. Both calls retry up to 3 times immediately.

Status UI on the Tenants list

An aggregate icon per tenant, rolled up from all tracked steps — green check (all succeeded), red X (nothing succeeded, at least one failed), amber warning (mixed), gray clock (nothing finished yet). A tenant with no tracked steps (a legacy tenant created before this feature shipped) renders no icon at all, not a permanent clock. Clicking opens a SweetAlert2 dialog listing every step's name/status/message/timestamp, sourced from the DataTable's own row data on click — never embedded as a data-* attribute, since the sections JSON's embedded quotes would break naive attribute escaping.

09

Known rough edges

Worth knowing before you touch this code.

Real risk

Connection-string password desync, three layers deep. The Postgres role's password is never ALTER'd if the role already exists (§03); UpdateConnectionStringsAsync only rewrites the encrypted DB row and never touches Postgres; and Metabase's own database record is never refreshed with a new password on a re-enqueued/retried registration (no PUT /api/database/{id} exists in MetabaseApiClient at all). A password change made through the UI can silently fail to propagate to either system that actually needs it, with no error until something tries to connect.

Real risk

Tenant deletion leaves orphaned resources. DeleteAsync removes only the ABP Tenant row — no Postgres database/role cleanup, no Metabase deregistration. Compounds the licence-plate uniqueness check (§03), which only looks at currently-existing tenants, not orphaned roles from a deleted one.

Unenforced

Tenants.ManageFeatures/ManageEndpoints are declared but not found wired to any [Authorize] in this module — reserved/scaffold constants, not active gates.

Unused capability

DynamicUrl.TenantId supports per-tenant endpoint overrides in the schema; every actual call site passes tenantSpecific: false today — global-only in practice.

Inconsistent

The Reconciliation page uses a plain [Authorize] with no specific policy — every other page in this module names an explicit permission or IT role.

By design

PostTenantCreationStepStatus.Failure is reserved for a future step reporting a handled non-exception failure — unreachable today since the one step (Metabase) either succeeds or throws.

Missing

No UI to retry a failed post-creation step — an operator must manually re-enqueue a PostTenantCreationStepArgs directly. A "retry" action reachable from the status detail dialog (§07) would be a natural addition, now that step failures are visible in the UI at all.
