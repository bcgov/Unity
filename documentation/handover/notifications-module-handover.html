Unity.Notifications

Nothing calls CHES from a request thread. Every email Unity sends is a database row first, a queue message second, and an API call third — and that row is the audit record, the retry token, and the thing the UI lists. This page is the complete reference: the send pipeline, S3 attachments, scheduled notifications, the SignalR half, and the rough edges.

01

The pattern

Unity has to talk to people outside the browser session — applicants receiving decisions and reminders, staff receiving payment and failure summaries, operators pushing a maintenance banner into a live browser. This module owns all of it. Whatever the trigger, an email always travels the same four stages, and the EmailLog row created at stage two is what every later stage reads and writes.

01 · Publish
EmailNotificationEvent local event bus · EmailAction says which kind
02 · Materialise
EmailNotificationHandler own transactional UoW · writes the EmailLog
03 · Queue → 04 · Send
EmailQueueService → EmailConsumer RabbitMQ, then CHES; response written back

Three orderings inside stage two are load-bearing and worth preserving if you touch that file:

Validate twicebefore mutating, before committing

The first attachment check fails a send of an existing draft before any S3 object is copied. The second fails before the unit of work commits, so a missing object rolls back the transition out of Draft and the user can re-upload.

Own unit of workrequiresNew: true

The log row and its attachment rows commit or roll back as one, independently of whatever transaction the publisher was in.

Queue after commitoutside CompleteAsync

The consumer can never dequeue a message whose EmailLog row is not yet visible to it.

The one path that skips all of it

ExceptionLogAppService calls SendEmailNotification directly for exception alerts — no log row, no queue. SendCommentNotification does the same for @-mention emails, rendering an embedded CommentNotification.cshtml resource by string replacement rather than through EmailTemplate.

02

Two halves, one module

Read this as two modules that happen to be co-located. They share a project set, a database schema, and a feature-flag family — and no code paths at all.

Email half
Compose, template, schedule, queue, send via CHES, retry, audit. Attachments in S3. Gated by the Unity.Notifications feature and the Notifications.* permissions.
Realtime half
A SignalR hub tracking who is online, delivering operator-to-user and operator-to-tenant messages, persisting every delivery as a NotificationLog. Gated by the Unity.Notifications.DirectMessaging feature and the ITOperations role — not by any module permission.

Dependency direction

Domain.Shared enums, feature consts, NotificationsResource localization ↑ Domain entities, repository interfaces, setting definitions, NotificationReadStateManager, seed contributors ↑ Application.Contracts DTOs, app service interfaces, NotificationsPermissions ↑ Application managers/services, CHES client, RabbitMQ producer + consumer, S3 attachment service, the local event handler ── references Unity.GrantManager (see below) ── ↑ EntityFrameworkCore ConfigureNotifications() model extension + custom repositories ↑ Web Razor Pages, NotificationHub, presence tracker, UnityMessagingController, menus, settings view component

The module defines the plumbing; the host defines when

Unity.Notifications.Application knows how to build, queue and send. It does not know that grant applications exist. That knowledge lives in the host, which publishes the events:

Host componentTrigger
Notifications/EmailAppServiceA user clicks Send or Save Draft in the application email widget
GrantApplications/BulkEmailNotificationAppServiceA user sends a batch of per-application drafts
Events/ScheduledNotificationEventHandlerAn ApplicationChangedEvent or PaymentStatusChangedEvent matches a configured event-based notification
Events/DateBasedScheduledNotificationJobA nightly Quartz job finds applications whose configured date field has passed
Logs/ExceptionLogAppServiceA new, not-recently-seen exception is logged
Unity.Payments · FsbPaymentNotifierPayments reach FSB status, or a payment batch fails

The exception to that rule — EmailNotificationHandler lives in Unity.Notifications.Application/Events/ but declares namespace Unity.GrantManager.Events and injects IRepository<ScheduledNotification, Guid>, a host entity. Unlike Flex and TenantManagement, this module cannot be used without the host. See §09.

External dependencies

CHESCommon Hosted Email Service

The only way mail leaves Unity — there is no SMTP anywhere. Base URLs come from DynamicUrl rows (NOTIFICATION_API_BASE, NOTIFICATION_AUTH) resolved through the host's IEndpointManagementAppService, so they are configuration, not constants.

POST /emailGET /status?msgId=DELETE /cancel/{id}
RabbitMQ

Decouples send from request, and carries the retry. EmailQueueService produces, EmailConsumer consumes. TTL 10 minutes first pass, 20 on retry.

S3

Attachment bodies. Path-style addressing, ForcePathStyle = true, no AWS region — an S3-compatible store, not AWS proper.

Redis

SignalR backplane so realtime messages cross pods. Standard or Sentinel; channel prefix defaults to unity:signalr. Note it carries messages, not presence — see §07.

Keycloak / IDIR

Resolving sender and recipient display names and email addresses for email groups, message senders, and the tenant roster.

03

Domain model & schema

Every entity implements IMultiTenant. No query in this module filters TenantId by hand — ABP's automatic filter does the isolation, and the few places that step outside it do so deliberately via ICurrentTenant.Change.

Two DbContexts, one of which is the real one

NotificationsEntityFrameworkCoreModule registers a NotificationsDbContext, but at runtime the tables are created and queried through the host's GrantTenantDbContext, which calls the same modelBuilder.ConfigureNotifications() extension from its own OnModelCreating. Tenant migrations carry the notification tables; the module's own context is a scaffold that keeps the module self-describing. Schema Notifications, empty table prefix.

Core entities

EmailLogAuditedAggregateRoot<Guid>

One outbound message, and the unit of work for the whole pipeline. Addresses are comma-joined strings, not collections. Holds the rendered body, the CHES response/status/msgId, the retry count, and links to an application, an applicant, and optionally a ScheduledNotification.

EmailLogAttachment

Metadata for one S3 object. EmailLogId or TemplateId is set. OriginTemplateId records that the row was copied from a template — which is what makes template re-application replaceable. Cascade-delete FKs to both parents; indexed on S3ObjectKey to support the shared-object reference check.

EmailTemplatethe only soft-deleted entity

Tenant-scoped name, subject, HTML and text body, send-from, recipient category/identifier. Can own attachments. Body tokens are {{token}} placeholders.

EmailAddressConfiguration

An allowlisted address with a type. Two indexes matter: (TenantId, EmailAddress, EmailType) unique, and a filtered unique index on TenantId where "IsDefault" = true — at most one default per tenant enforced by Postgres, not just by service code.

EmailGroup+ EmailGroupUser

A named list of internal users. FSB-AP and Payments are seeded per tenant. A group referenced by an active scheduled notification cannot be deleted — but it can be renamed, which silently breaks the link (§09).

NotificationLog

The durable record behind the Notification Logs page. Three enums stored as strings, PayloadJson as Postgres jsonb, indexes on (TenantId, CreationTime), (NotificationType, CreationTime) and CorrelationId.

NotificationReadState

One row per (tenant, user) holding LastReadAt. Its manager is the module's only domain service, and it deliberately swallows AbpDbConcurrencyException — two tabs advancing the same watermark is expected, and losing one write is harmless.

The EmailStatus lifecycle

EmailStatus is a static class of string constants, not an enum — stored as free text with no length or check constraint.

InitializeDraft ───────────────► Draft ──(SendCustom)──► Initialized ─────► Sent (CHES 2xx) or Scheduled ├────► Failed (CHES error · retries │ │ exhausted · missing │ │ attachments) └────────┴────► Cancelled (user cancels a non-Sent email)

Created is the seventh constant and is never assigned anywhere.

The send pipeline

Stage detail. The most consequential logic in the module is EmailConsumer.ProcessEmailAsync's failure classification — it decides what gets another attempt and what is dead on arrival.

Which EmailActions are actually routed

SendFailedSummaryHandleFailedSummaryyes

Failure classification in the consumer

FailureStatusRetried?
RetryAttempts > 10Failedno — give up
MissingEmailAttachmentsExceptionFailedno — a missing object stays missing
AmazonS3ExceptionFailedyes — transient storage
Any other send exceptionFailedyes
CHES 429 · 500 · 502 · 503 · 504as returnedyes
Any other CHES statusSent (2xx) or Failedno

Status is set to Failed before a retry is scheduled, so a message mid-retry reads as Failed in the UI until an attempt succeeds.

Three defensive details in UpdateEmailLogStatus

Scheduled is preserved

A scheduled email whose SendOnDateTime has not passed keeps status Scheduled regardless of the response. CHES has accepted it for later delivery; flipping it to Sent would be a lie. Only once the send time passes does the response decide.

The Date header is untrusted

SanitizeResponseDateTime rejects a CHES Date header more than 5 minutes in the future or 15 in the past and substitutes UtcNow — an external system's clock treated as input, not fact.

Payments get told

A successful send with non-empty PaymentRequestIds publishes FsbEmailSentEto back on the local bus so Unity.Payments can mark those requests notified.

Building the CHES message object

cc and bcc are included only when present — CHES wants arrays, never null. templateName is stored on the log but deliberately excluded from the payload: it is not part of the CHES MessageObject schema. A scheduled send adds delayTS as Unix milliseconds.

Cancelling a scheduled email — the careful path

Deleting a scheduled email that already has a ChesMsgId first asks CHES for the real state rather than assuming:

CHES statusWhat Unity does
completed / acceptedAlready out. Mark the log Sent, persist, and refuse the delete with a user-friendly error.
pendingStill queued at CHES. Call CancelEmailAsync to withdraw it; a failed cancel throws rather than deleting a row for a message that will still arrive.
anything elseRecord the status and proceed with deletion.
unexpected exception"Unable to verify the status of the scheduled email." Refusing to delete blind is the safe default.

Its softer sibling doesn't do this. CancelEmailLogAsync just sets Status = Cancelled without calling CHES — so cancelling a scheduled email through that path leaves the message queued at CHES to be delivered anyway.

05

Attachments

Bytes in S3, metadata in Notifications."EmailLogAttachments". Metadata is the source of truth; orphaned bytes are an accepted cost.

Email/Attachments/{tenantId|host}/{emailLogId}/{attachmentGuid}/{fileName} ← user uploads Email/FSB-AP-Payments/{tenantId|host}/{emailLogId}/{fileName} ← generated FSB spreadsheets

The user path interposes a fresh Guid per upload, so two files with the same name never collide and every copy of a template attachment gets its own object.

A considered asymmetry on missing users

UploadAttachmentAsync
Reached from the event handler, which runs for schedule- and system-triggered emails. A null ICurrentUser.Id becomes Guid.Empty — there genuinely may be no interactive user, and the caller already sends without the attachment on any failure.
UploadUserAttachmentAsync
Reached from an authenticated HTTP upload. A null id throws AbpAuthorizationException — attributing a user-uploaded file to Guid.Empty would look like a valid, specific user rather than an error.

Copy vs. replace

CopyTemplateAttachmentsadditive

Deduplicates by (FileName, FileSize, ContentType) among rows whose OriginTemplateId matches — not by S3ObjectKey. Every copy gets a brand-new key, so a key-based check would never match and a re-run would duplicate everything.

ReplaceTemplateAttachmentsordering is the point

Validate every source exists → copy all to fresh email-owned objects → only then delete the previous template-origin rows. Manually uploaded draft attachments have no OriginTemplateId and are left untouched.

On any copy failure

DeleteCopiedObjectsBestEffortAsync removes the objects already written, then rethrows — a partial copy never leaks storage.

Four validation points, four different races

EmailAppService.SendAsync — HTTP boundary Handler — before mutating Handler — before committing QueueEmailAsync — before the broker Send time — non-retryable failure

Existence is checked with GetObjectMetadataAsync (a HEAD, not a GET), and IsMissingObject treats 404, NoSuchKey and NotFound alike because S3-compatible stores disagree on which they return. All missing files surface in one MissingEmailAttachmentsException, worded differently for a template than for an email.

Deletion is reference-aware

Ask whether any other metadata row points at the same object → delete the row (a missing row is success) → if others still reference it, stop → otherwise delete the object, and if that fails, log and do not rethrow. The invariant, stated in the source: the database must never retain a key merely because best-effort storage cleanup failed; a leaked object is safer than deleting one another attachment still needs.

The permission is not the control on upload. EmailLogAttachmentAppService.UploadAsync is [RemoteService(false)] because it takes raw filename/content/type with none of the allowlist, size or content-type checks AttachmentController enforces. Exposing it would let a caller holding a legitimate Email.Send permission bypass validation entirely.

06

Scheduled notifications

"Scheduled notification" here means a configuration, not a queued message: when applications on form X reach status Y — or when date field Z passes — render template T and send it to recipients R. All of it lives in the host; both triggers converge on publishing an EmailNotificationEvent.

Trigger A · Event
ScheduledNotificationEventHandler ApplicationChangedEvent · PaymentStatusChangedEvent
Converges on
ScheduledNotificationHelper token render + recipient resolution → publish
Trigger B · Date
DateBasedScheduledNotificationJob nightly Quartz, default 0 0 2 * * ?

Recipient resolution

Internal
RecipientIdentifier is a comma-separated list of email group names. Groups → members → identity emails, accumulated into a case-insensitive set. A missing group, an empty group, or a failed user lookup each log a warning and skip rather than failing the batch.
External
Two recognized literals: ApplicationContact → ApplicantAgent.Email, and SigningAuthority → Application.SigningAuthorityEmail. Anything else logs and skips.

Zero resolvable addresses means nothing is published at all — no EmailLog row is ever created, so the silence is invisible outside the logs.

Token substitution

A compile-time [GeneratedRegex(@"\{\{(\w+)\}\}")] replaces tokens against a hand-written dictionary built from the application and applicant agent. Unknown tokens are left in place — a typo renders as literal {{typo}} rather than a blank. Navigation-property access is wrapped in try/catch because the entity may have been loaded without details.

The seeded TemplateVariable.MapTo column documents intent but is not what resolves the value — the dictionary is. Adding a variable takes two edits: a seed row and a dictionary entry.

Duplicate suppression, and its two gaps

ScheduledNotificationTracking is the ledger, keyed by (ApplicationId, ScheduledNotificationId, DateField) — which is why one application can be notified separately for its due date and its contract date. Two consequences:

  • A tracking row is created when the event is published, not when the email is sent. A later permanent pipeline failure still reads as "notified", and the job will never retry it.
  • Rows are inserted in one batch at the end of each tenant's run, so a crash mid-run loses the whole batch and those applications are notified again next time.

The date job is written explicitly to avoid N+1: one application query across all forms, one tracking query, one template load, one applicant-agent load, and one batched insert at the end.

07

Realtime & logs

The second half. A SignalR hub at /signalr/notifications, a per-pod presence tracker, and a durable log of every delivery. The feature check runs at connect time — a disabled tenant gets Context.Abort(), not merely a hidden menu item.

Groups, and what they mean

user:{userId} every connection joins its own tenant:{tenantId} joined when a tenant is in context ops:notification-logs joined only by ITOperations users

These same strings are persisted as NotificationLog.DeliveryTarget, so a log row records exactly which group the message was pushed to.

Hub surface

MethodAuthorizationBehaviour
GetUnreadMessagesAsyncany connected userUp to 50 messages after the caller's LastReadAt, addressed to them or tenant-wide
GetConversationHistoryAsyncany connected userUp to 100 — tenant broadcasts, or the two-way thread with one peer

Cross-tenant safety on peer messages needs no manual TenantId check: ABP's automatic filter applies to the repository lookup, so a user outside the current tenant comes back null even when the Guid is valid. Adding a comparison would be redundant.

Presence is per-pod

NotificationPresenceTracker is a singleton holding ConcurrentDictionarys keyed {tenantId|host}:{userId}. The Redis backplane fans out messages across pods — it does not carry presence. With more than one replica the online list shows only the users connected to the pod that served the request, and the operator cannot tell what they are missing.

UnityMessagingController partly compensates: it lists each tenant's full roster and derives "last activity" from the ABP audit log rather than from presence, so offline users still get a meaningful last-seen. Its IsOnline flag has the same blind spot.

The two API-key endpoints

message-tenant-api and message-all-tenants-api are [AllowAnonymous] at the ASP.NET level and authenticate themselves, so an external operations tool can push a maintenance banner without an interactive login:

Constant-time compare

The header key is compared to the decrypted tenant token with CryptographicOperations.FixedTimeEquals over UTF-8 bytes — the comparison does not leak key material through timing.

Feature re-checked inside the target

message-tenant-api re-enters the target tenant's context to verify DirectMessaging before sending, and returns 403 if it is off. The broadcast endpoint authenticates against the default grant program tenant's key and skips every tenant with the feature disabled, returning the list it actually delivered to.

09

Known rough edges

This module carries more accumulated scaffolding than most — an unfinished subscription model, a Teams integration that was disabled rather than removed, and two halves built at different times to different standards. Ordered by real-world risk.

Real risk

Retry backoff is an in-process Task.Delay. Five minutes × attempt number, awaited inside the consumer's own unit of work — holding a database connection and transaction open for up to 55 minutes on the tenth attempt. The delay is process-local, so a pod restart loses the retry entirely and the row stays Failed with nothing queued to revive it. On later attempts it also exceeds the message's own 20-minute TTL.

Real risk

The configured retry limit is not the one that applies. The settings tab exposes Maximum Email Retry Attempts; nothing reads it. EmailConsumer uses its own const int maxRetries = 10. Lowering the setting changes nothing — a control that appears to work and does not.

Real risk

Hard-coded −7 timezone offset. NormalizeToUtc treats an Unspecified send time as BC's permanent daylight offset — legislated but not adopted. From November to March the province is still PST (−8), so an email scheduled for 9:00 AM in January is delivered at 8:00. The host's NotificationListAppService does it correctly with TimeZoneInfo; the two should agree.

Performance

GetPendingEmailsCountAsync loads every email log. It builds an expression, then compiles and applies it in memory — materialising the tenant's entire email history to produce one integer, on a schedule, from the health-check worker.

Multi-pod

Presence is in-process memory behind a Redis backplane. Messages cross pods; presence does not. Invisible at one replica, a partial view at more.

Declared, never written

Log types and channels for pipelines that don't exist. Ten NotificationLogType values and four channels; only SignalRDirectMessage/SignalR are ever written. The Logs page offers all of them as filters, so an operator can filter to DbException and always get nothing. Meanwhile the exception path that does exist writes to a separate table and never touches NotificationLog.

Dead scaffolding

The subscription/trigger model is mapped but unused. Trigger, TriggerSubscription, Subscriber, SubscriptionGroup, SubscriptionGroupSubscription — entities, FKs, and tables in the initial migration; zero references. Superseded by ScheduledNotification. Removing them is a migration, so it needs a decision rather than a passing cleanup.

Dead scaffolding

A duplicate DynamicUrl stack nothing registers — entity, repository interface, repository, and a second GrantManagerDbContext, all self-referential and never wired up. It shares a class name with the host's real context, so a careless using could bind to the wrong type.

Silent

The Teams integration is disabled, not removed. PostToNotificationsChannelAsync has a fully commented-out body. Everything upstream still runs — reading the card template off disk, building the MessageCard JSON, looking up a channel URL — and the result is discarded. Two live callers (CHES errors, CHEFS form-publish events) believe they are alerting someone.

Silent

Renaming an email group breaks its scheduled notifications. The link is by name. Deletion is guarded; renaming is not. Every notification pointing at the old name resolves to zero recipients, logs a warning, and publishes nothing.

Silent no-op

EmailAction.Retry, SendByTemplateId, SendApproval and SendDecline are declared, unrouted, and never published. A future caller reaching for SendApproval because the name fits gets nothing, silently — a default: branch that logged would at least make it visible.

Dead columns

EmailLog.AssessmentId and ApplicantId are never assigned. The list service reads ApplicantId with a fallback, so only the fallback branch is ever taken; AssessmentId has no reader at all.

Confirm intent

[AllowAnonymous] sits on the interface declarations of IEmailGroupsAppService.GetListAsync and IEmailGroupUsersAppService.GetEmailGroupUsersByGroupIdAsync, overriding the class-level [Authorize]. Whether anonymous access to the tenant's internal email-group roster is intended is worth confirming.

Architecture

The handler lives in the wrong module. EmailNotificationHandler sits in the Notifications project but declares a Unity.GrantManager.Events namespace and injects a host entity, so this module cannot stand alone the way Flex and TenantManagement can. An IScheduledNotificationLookup contract defined here and implemented in the host would apply the same inversion those modules already use.

Coverage

EmailAttachmentServiceTests is the only file with tests. Status transitions, retry classification, CHES response parsing and scheduled-send cancellation — the module's highest-risk logic — have none.
