Unity.AI

Six named operations against an Azure OpenAI deployment, every one of them queued behind four independent gates, retried three times against a shape validator, and delivered as a draft a human still has to accept. What model to call, how many tokens it may spend, and the exact prompt text are database rows — not code. This page is the complete reference.

01

Six operations

Grant assessment is reading — a submission, a scoresheet to fill in, and a dozen attached PDFs, read the same way by different assessors at different speeds. This module produces the first draft. Three operations act on an application; three act on an application form version, generating the configuration artefacts programs otherwise hand-build.

The line the module holds

AI output is a draft. Application scoring lands as a separate AI assessment sitting beside the human ones, never as somebody's score. The three form-generation operations write a GenerationReview that a person must complete or discard — nothing the model produces reaches an application form on its own. Summaries and analysis surface behind a legal disclaimer the user acknowledges before AI is switched on at all.

Token budgets above are the seeded AIOperation.CompletionTokens values, and they encode how much output each operation is expected to produce — scoring and scoresheet generation get four times the budget of a mapping suggestion.

Seven features, three settings, fourteen permissions

Unity.AI.AttachmentSummaries Unity.AI.ApplicationAnalysis Unity.AI.Scoring Unity.AI.FormMapping Unity.AI.FormWorksheet Unity.AI.FormScoresheet Unity.AIReporting

All default "false". Every AIPermissions entry carries .RequireFeatures(...) for its matching feature, so turning a feature off also removes its permissions from the role editor. SettingManagement.ConfigureAI uses an AnyFeaturePermissionStateProvider across all seven — it appears when any one is on.

AutomaticGenerationEnabled
The intake pipeline may fire on its own. Required together with the form's AutomaticallyGenerateAIAnalysis flag.
ManualGenerationEnabled
Staff may trigger generation by hand. Pairs with the form's ManuallyInitiateAIAnalysis flag.
ReportingEnabled
The AI Reporting page is reachable — feature and setting, or the ITAdmin role as an override.

Permissions come in View / Generate pairs per operation, Generate nested under View. That split is load-bearing on the application detail page: the tab and existing results are gated by View, the button only by Generate — so somebody can read an analysis produced automatically at intake without being able to regenerate it.

Prompt administration sits outside all of this. AIPromptAppService is gated by the ITOperations role, not by an AI permission or feature, and the menu item is hidden entirely when the Onboarding specialization is enabled.

Only the endpoint and the API key come from configuration. Which model an operation calls, how many completion tokens it may spend, whether it fans out sequentially or in parallel, and the exact system and user prompt text are all rows.

All six operations bind to gpt-5-mini. Those two model settings exist because newer families reject the parameters older ones require — when MaxOutputTokenCountSupported is false the option is not sent at all rather than defaulted, and the same for a null temperature. The model name is also the Azure deployment name: the factory passes it straight to GetChatClient(...).

All three seeders skip tenant contexts and are corrective — an existing model or operation row has its provider, active flag, settings, model binding, execution mode and token budget overwritten on every run. There is no admin UI for models or operations; changes made directly in the database are reverted at the next migration run.

Two AI schemas, in two databases

The single most surprising fact about AI persistence. ConfigureAI() is called on GrantManagerDbContext — the host context — while the tenant context declares its own AI tables explicitly.

DatabaseSchema AI holds
HostAIModels · AIOperations · AIPrompts · AIRequests
TenantGenerationReviews · ApplicationScoresheetAnswers

Two consequences worth carrying: AIPrompt implements IMultiTenant but lives in the host database, so every read path disables ABP's tenant filter and re-applies tenancy by hand — automatic isolation protects nothing here. And AIRequests references applications that live in a different database, so no foreign key exists or can. Schema changes split accordingly: model/operation/prompt/request are host migrations, reviews and scoresheet answers are tenant migrations.

04

The pipeline

Every operation travels the same path, and nothing calls the model on a request thread. AIGenerationAppService.SubmitAsync is the single funnel every typed route converges on — the source comment says so: "All generation routes converge here so authorization, feature, and form-version rules stay consistent."

AIGenerationAppService.SubmitAsync feature guard · form-version guard · CheckPolicy

The lock covers the dedupe check

var requestLock = distributedLockProvider.CreateLock( $"ai-generation:{tenantId}:{request.ApplicationId}:{persistedOperation.Id}"); using (await requestLock.AcquireAsync()) { if (existing Queued|Running request) return; // silently idempotent await validateInput(); // prerequisites await aiRateLimiter.EnsureAsync(currentUser.Id); // insert AIGenerationRequest (Queued), then enqueue the job }

The comment in the source is explicit about why the lock spans the check — "so each tenant/application/operation queues only once." Without it two clicks a millisecond apart both see no active request and both enqueue. Note the ordering: prerequisites are validated before the rate limit, so a request that was going to be rejected anyway never costs the user their cooldown.

Prerequisitesper operation

Attachment summary needs at least one attachment; analysis needs a non-empty submission; scoring needs a scoresheet with fields; the three form operations need the form version to exist and no Active review. Each throws its own localized message.

Rate limitper user, distributed

A cooldown in the distributed cache at ai-generation:cooldown:{userId}, read-modify-written under its own distributed lock. Length comes from Azure:Generation:CooldownSeconds, which must be configured — the getter throws otherwise. Stamped only after a successful run, so a failure does not cost the next attempt. A null user (background/system) bypasses it entirely, by design.

Short units of workrequiresNew, non-transactional

Every status transition and every result save opens its own brief UoW. The helper explains why: holding the Application aggregate loaded across a slow model call reliably produced AbpDbConcurrencyException when unrelated parts of it changed concurrently.

Executor registrySingleOrDefault

Six IAIGenerationOperationExecutor implementations resolved from DI by exact operation type. Two executors claiming the same type is a startup-time bug that surfaces as a runtime throw.

Automatic, at intake

QueueApplicationAIPipelineOnProcessHandler short-circuits in order on the tenant setting, the form flag, then all three intake features being off. Otherwise it queues attachment summary, analysis and scoring — each in its own try/catch, throwing only if no feature was enabled or every enabled stage failed to queue. The handler then catches anything that escapes, so a failed AI pipeline never fails intake.

They are queued as three peers, not a chain — even though analysis and scoring both consume attachment summaries as input. See §08.

05

Calling the model

The provider is Azure OpenAI with key auth, one deployment per call. The Provider string stored on the model and checked by the transport is nevertheless "OpenAI" — it names the model family, not the hosting service.

new AzureOpenAIClient(settings.Endpoint, new ApiKeyCredential(settings.ApiKey), new AzureOpenAIClientOptions()) .GetChatClient(settings.DeploymentName)

A 200 is not success

The model is asked for JSON, and JSON from a language model is not trustworthy. Every call is wrapped in up to three attempts, and an attempt that returns HTTP 200 still fails if the payload does not validate against the operation's expected shape.

for attempt in 1..3 result = await transport(...) if Success: validation = validator(result.Content) // per-operation shape check if valid → return else → downgrade to InvalidOutput, log the reason, retry if PermanentFailure → return immediately // no point retrying a 401 if attempt < 3 → loop (no delay)

AIResponseJson.CleanJsonResponse strips markdown fencing before parsing, because models return fenced JSON regardless of instructions. OperationCanceledException is always rethrown, never mapped.

Two defensive touches worth keeping

Temperature fallbackone retry, on 400

Newer model families reject temperature outright. Rather than encode a model-family table, the transport inspects a 400 body for "temperature" plus one of unsupported / not supported / not allowed / invalid, and if it matches, retries once without the parameter. Anything else rethrows.

Output read twice over

First the SDK's typed completion.Content[i].Text parts; if that yields nothing, the raw body is parsed for choices[0].message.content in both its string and array-of-parts forms. An empty output is then logged with finish reason and the full token usage including reasoning_tokens — which is what makes a truncation or a reasoning blowout diagnosable after the fact.

Text extraction is local

No document-intelligence service. PDFs via PdfPig, Office formats via NPOI and raw OpenXML, dispatched by extension and falling back to content type.

.pdf.docx.xls / .xlsx .pptx.txt / .csv / .json / .xml .doc — returns empty

Hard caps guard the token budget: 50,000 characters overall, 10 Excel sheets, 2,000 rows per sheet, 2,000 docx paragraphs, 200 PowerPoint slides. Any extraction failure returns an empty string, which the summary service treats as "could not extract".

06

Prompts

A prompt family is an AIPrompt.Name equal to an operation name; versions are integers rendered as v{n}; (TenantId, Name, VersionNumber) is unique. Seeded globally at v0–v2 for the three application operations and v2 for the three form operations, so an older result can be reproduced by pinning a version.

A tenant prompt wins outright

selected = tenant's newest ACTIVE prompt in this family selected ??= global (TenantId == null) newest ACTIVE prompt in this family

If the tenant has any active prompt in the family, the global rows are not considered at all — including when the global family has a higher version number. A tenant that once saved a tweak to ApplicationScoring stops receiving every subsequent global improvement, with nothing in the UI indicating the divergence.

Rendering, and how it fails

The system prompt is sent verbatim; the user prompt is a template of {{TOKEN}} placeholders. Each operation supplies its own set — SCHEMA, DATA, ATTACHMENTS, ATTACHMENT, SECTION, RESPONSE/OUTPUT (aliases of each other) — and any named section in the prompt's MetadataJson becomes a placeholder too, which is how the form-generation prompts keep large reusable rule blocks tenant-editable but out of the template.

An unresolved placeholder throws. Rendering scans the template first and fails loudly rather than sending a literal {{FOO}}. That maps to PermanentFailure, so a broken prompt fails immediately instead of burning three attempts — but nothing validates a prompt when it is saved, so the error appears on the next generation rather than on the form.

Scoring gets an extra layer

Scoresheet question ids are GUIDs. Before the section reaches the prompt, BuildAliasedApplicationScoringSection swaps them for short tokens and returns a map the parser uses to translate answers back. Each field is projected with its options and allowed_answers for SelectList questions — which is what constrains the model to a valid option rather than free text. If the response template builds to "{}", the operation logs a warning and returns without calling the model.

07

Where results land

Executors return a bool: true stamps the user's cooldown, false completes the request without charging them — used when the executor decided there was nothing to do.

application-analysis

Written to Application.AIAnalysis in a fresh short unit of work. The only operation that throws on provider failure, so the only one where a failed model call marks the request Failed and shows the user an error.

application-scoring

Upserted into AI.ApplicationScoresheetAnswers — one row per application, whole answer set as jsonb. Its own doc comment records why it moved off the Application aggregate: "so the Applications table stays legible to report builders, and so AI output is not written back onto the Application aggregate." Then publishes ApplicationAIScoringGeneratedEvent, which creates an AI assessment alongside the human ones.

attachment-summary

Persisted per attachment, fanning out over the operation's AIExecutionMode. Failure and empty-extraction both persist a sentinel string as the summary — see §08.

form-mapping

A GenerationReview payload of pending suggestions. Passes alternate by sequence: isFinalMapping = Sequence > 1 && Sequence % 2 == 0, and a final pass additionally classifies which suggestions leave the existing mapping unchanged.

form-worksheetand form-scoresheet

A draft Flex worksheet or scoresheet plus a review. The worksheet is written under a canonical name derived from the form version id, which is what makes the operation idempotent — a second run finds the existing suggestion and leaves it alone rather than duplicating it.

The review is a lock

An Active GenerationReview — keyed (Operation, ContextId, Sequence), status Active / Completed / Discarded — blocks another run of that operation for that form version. The prerequisite validator refuses to queue it, and the executor re-checks and returns false if one appeared in the meantime. This is the mechanism that keeps AI out of form configuration: nothing the model produces reaches an application form until a person completes the review.

The guided mapping workflow

GenerateInitialMapping → ReviewInitialMapping → GenerateWorksheets → ReviewWorksheets → PublishAssignWorksheets → GenerateFinalMapping → ReviewFinalMapping → Completed

Map what you can, generate worksheets for what you cannot, publish and assign them, then map again now that the new custom fields exist. The step names are localization keys in AILocalizationKeys; the odd/even sequence rule above is what implements the two mapping passes.

08

Known rough edges

This module is newer and far better covered by tests than most of the codebase, so this list is shorter on outright defects and longer on correct but surprising. Ordered by real-world risk.

Real risk

Failures are persisted as content. Four of six operations turn a provider failure into a successful result carrying a failure message, which is then stored as output: an attachment summary reading "AI analysis not available for this attachment (x).", an empty scoring answer set, a "{}" worksheet. The request is marked Completed, the cooldown is charged, and a later reader cannot tell "the model was down" from "the model said this". Only application analysis throws.

Real risk

A partly failed scoring run is saved as if complete. ProcessSectionAsync catches per-section exceptions and returns an empty dictionary. The merge produces an answer set silently missing those sections, upserts it over any previous complete run, and fires the event that creates an AI assessment from a partial scoresheet.

Real risk

The intake pipeline is three peers, not a chain. Attachment summary, analysis and scoring are queued as independent jobs with nothing ordering them — yet analysis and scoring both consume attachment summaries as input. On a first intake they typically read no summaries at all, and the prompt renders with an empty attachments block.

Performance

The retry loop has no backoff. Three attempts back to back with no delay and no jitter, including after a 429. AIExecutionMode.Parallel compounds it: Task.WhenAll over every section with no concurrency cap, so a twenty-section scoresheet issues twenty simultaneous calls, each of which may retry three times.

Multi-pod

Config caching is per-pod and holds the API key. The fully resolved settings — including ApiKey — sit in IMemoryCache for five minutes under a predictable key, with no invalidation on write. Activating a prompt version or switching an operation's model applies at a different moment on every replica.

Security

Tenant isolation for prompts is manual. AIPrompt is IMultiTenant but lives in the host database, so every read disables ABP's filter to allow the global fallback and re-imposes tenancy in LINQ or in EnsureReadAccess/EnsureMutationAccess. Any new query over AIPrompt must repeat the pattern; a missed check is a cross-tenant read of prompt text.

Confirm intent

Prompt file logging writes applicant data to local disk. When Azure:Logging:EnablePromptFileLog is on, the full rendered prompt — submission data, extracted attachment text — and the raw provider response are appended to {BaseDirectory}/logs/ai-prompts-*.log on every operation. Off by default; worth a deliberate decision before enabling anywhere holding real applications.

Silent

IsAvailableAsync only checks that a key is configured. It reads Azure:OpenAI:ApiKey and returns true. A wrong key, an unreachable endpoint, a missing operation row or an inactive model all still report available.

Silent

Form scoresheet does not check its outcome. Every other operation branches on result.Outcome before using the content; GenerateFormScoresheetAsync returns the cleaned content of a failure response as if it were a scoresheet, relying entirely on the caller noticing FailureReason. Its worksheet sibling returns "{}" in the same situation.

Silent

Duplicate submissions return quietly, with no way for the caller to distinguish "queued" from "already running". And MarkRunning/MarkCompleted both clear FailureReason, so a retried request loses the record of why it failed last time — the only trace is the log.

Hard-coded

The provider is fixed in three places despite AIModel.Provider being a column: the resolver returns the constant, the resolver rejects anything else, and the transport rejects it again. Three framings collide in one call path — an AzureOpenAIClient, a provider string of "OpenAI", and an Azure:OpenAI: config section. Deployment name must equal model name; there is no way to point a model row at a differently named deployment.

Dead code

Seven resolver accessors production never calls — four exercised only by tests, three by nothing. Five are unusable without an explicit model name anyway: ResolveModelAsync returns null for a blank name, so they throw "AI model is not configured." regardless of setup. Also unreferenced: the PromptType enum, which is not even a property of AIPrompt.

Ergonomics

Prompt text lives in a 973-line C# seeder of const string bodies — editing a seeded prompt means a code change, a build and a deploy, with unreadable diffs. The runtime already supports versioned rows, so the seeder is the only reason prompt text is compiled in. Meanwhile GetListAsync loads every prompt row and pages in memory, and models and operations have no admin UI at all.

Convention drift

Guid.CreateVersion7() instead of GuidGenerator in the prompt service and both seeders; DateTime.UtcNow instead of Clock throughout. Two naming schemes for the same six things (application-scoring vs ApplicationScoring) bridged by a definition record and re-exported by a key helper. Unity.AI.Domain.Shared builds Unity.AI.Shared.csproj. The permission provider sits in Application.Contracts, unlike every other module. And AIGenerationStatusDto returns its payload twice — nested and flattened.

Coverage

Unusually good, and worth preserving. Config resolution, prompt resolution and rendering, response validation, the outcome model, queue/job/registry/status, rate limiting, seeders, input building and execution mode all have suites. Thinner: the transport itself (temperature fallback, response extraction, status→outcome mapping), text extraction across formats, and the six executors end to end.
