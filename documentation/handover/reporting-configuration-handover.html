01

The pattern

Unity Portal stores form submissions, worksheet answers, and scoresheet answers as JSON. SQL cannot filter or aggregate on a field inside a JSON blob without knowing the schema. This module is how that schema gets declared — once, by a person, per reporting surface — and turned into an ordinary PostgreSQL view of flat, typed, named columns that Metabase (or Power BI, or anything else with a Postgres driver) can query without knowing anything about Unity.

Declare
ReportColumnsMap.Mapping one MapRow per field: path, type, column name
Generate
generate_*_view(correlationId) background job → stored procedure → CREATE VIEW
Grant
AssignViewRoleBackgroundJob GRANT SELECT to the tenant's reporting role

Nothing in the loop is implicit. A view exists only because someone saved a configuration and pressed Generate — which is the entire point of the design, and the difference from the path it replaces.

Glossary

CorrelationThe pair (CorrelationId, CorrelationProvider) that identifies one reporting surface. Unique per mapping — one configuration, one view.
ProviderOne of five IFieldsProvider implementations. Knows how to read field metadata from its source system and how to detect that the source has changed since the mapping was saved.
MapRowOne field-to-column mapping: Label, PropertyName, Type, Path, DataPath, TypePath, ColumnName, SourceOrder, plus VersionLabel/WorksheetName where relevant.
Path vs DataPathPath is the full key breadcrumb including container ancestors — the stable identity key for matching rows across saves. DataPath strips containers that don't exist in the actual JSON (panels, tabs, columns, fieldsets) and is what the SQL navigates. The UI column labelled "Path" shows DataPath.
ConsolidatedA provider whose CorrelationId is the Form ID rather than a version ID, producing one view that spans every version of the form.
View roleA real PostgreSQL role, per tenant, granted SELECT on generated views. Stored as the tenant-scoped setting GrantManager.Reporting.TenantViewRole.
(DK1), (DK2)…Uniqueness stamps a provider applies when two source fields resolve to the same key chain. Surfaced in the UI as a "duplicate keys" warning for an administrator to resolve.

The five providers

Each implements IFieldsProvider and registers itself under a lowercase string key. ReportMappingService resolves them into a dictionary at call time and throws ArgumentException for anything unrecognised. Note which ones correlate on a version and which on a form — getting this wrong is the most common source of "no mapping found" errors.

Only formversion uses the field Key. The check is an exact case-insensitive match on the string "formversion", so formversion_consolidated deliberately does not match and falls through to Label. Server (ReportMappingUtils.GetDefaultColumnNameSource) and client (getDefaultColumnNameSource in Default.js) implement this identically, with no Key↔Label fallback in either — so an unsaved table and a saved configuration always agree.

How consolidated merging works

Fields from each version are matched on the triple (Label, Path, Type):

The version bookkeeping lives in Mapping.Metadata.Info as formversion_{versionId} and (for consolidated worksheets) ws_{versionId}_{worksheetId} keys, written at save time. DetectChangesAsync diffs those stored keys against live state — see §08.

04

Fields & column names

A column name has to survive PostgreSQL's identifier rules, stay unique within the view, and — critically — stay stable once a Metabase report depends on it. The pipeline is built around that last constraint.

Sanitisation, in order

1 spaces and hyphens → underscore 2 drop anything that isn't a letter, digit, or underscore 3 collapse repeated underscores 4 trim leading/trailing underscores 5 if nothing is left → "col" 6 if it starts with a digit → prefix "col_" 7 truncate to 60 chars, then trim a trailing underscore 8 lowercase 9 on collision, append _1, _2, … (suffix length is reserved during truncation)

Null or whitespace input short-circuits to col_1. The 60-character ceiling leaves room inside PostgreSQL's 63-character identifier limit for the uniqueness suffix.

Three-tier priority on save

1 · User-provided

A name the administrator typed in this save operation. Always wins.

2 · Existing

The name already persisted for that field Path. This is what makes established mappings immune to a provider changing its defaults.

3 · Auto-generated

Only for fields not covered by 1 or 2 — i.e. genuinely new fields discovered since the last save.

Validation (client and server both enforce)

≤ 60 characters starts with letter or underscore letters, digits, underscores only not a PostgreSQL reserved word unique within the configuration

ValidateMappingFields has one asymmetry worth knowing: duplicate keys alone and duplicate paths alone each only log a warning; the ArgumentException is thrown when both are true simultaneously. Duplicate column names and non-conforming names always throw.

Worksheet ordering is deterministic: worksheet name A–Z, then section order, then field layout order, then checkbox-option order, then data-grid column order (CHEFS-extracted dynamic columns first, then statically-defined ones). 05

View generation

Saving a configuration writes a row. Generating a view is a separate, explicit act — asynchronous, status-tracked, and safe to repeat.

GenerateViewAsync(correlationId, provider, viewName) ├─ resolve provider → ArgumentException if unknown ├─ normalise viewName to lowercase ├─ IsViewNameAvailableAsync(name, correlation) → ArgumentException if owned by another correlation ├─ map.ViewName = name; map.ViewStatus = GENERATING; save └─ enqueue GenerateViewBackgroundJobArgs { correlationId, provider, tenantId, originalViewName } (1s delay) GenerateViewBackgroundJob (in tenant context) ├─ find map by correlation → warn + return if gone ├─ if originalViewName differs → drop the old view (failure only warns; generation continues) ├─ repository.GenerateViewAsync → CALL "Reporting".generate_*_view(correlationId) ├─ ViewStatus = SUCCESS └─ enqueue AssignViewRoleBackgroundJobArgs { viewName, tenantId } catch → ViewStatus = FAILED, logged

Each procedure reads its mapping row out of Reporting."ReportColumnsMaps", raises if the mapping or its Rows array is missing, asks the data function for a complete SELECT statement, then DROP VIEW IF EXISTS "Reporting".{name} followed by CREATE VIEW "Reporting".{name} AS {statement} — both schema-qualified.

Where the values actually come from

formversion
formversion_consolidated

worksheet

None of these read a pre-flattened snapshot. The views query source tables directly, which is why the deprecated path's ReportData columns can be dropped without touching a single explicitly configured view.

Two availability checks

GlobalIsViewNameAvailableAsync(name)

True when no view of that name exists in pg_views under Reporting. Used for name suggestions before anything is saved.

Correlation-awareIsViewNameAvailableAsync(name, id, provider)

True when no mapping claims the name, or the claiming mapping is this same correlation. This is what lets a view be regenerated under its own name without a false conflict.

Delete

DeleteAsync drops the view first (a failure here is logged and downgraded to a warning message on the result) and then removes the mapping row unconditionally. Deleting a configuration is therefore always successful from the user's point of view, even if the database view survives — worth knowing when a name later appears "taken".

06

Roles & database access

A generated view is invisible to Metabase until a database role can read it. Role assignment is per tenant, stored as an ABP setting, and applied by the second background job.

GrantManager.Reporting.TenantViewRole
Tenant-scoped ("T") setting naming the PostgreSQL role. The current mechanism.
GrantManager.Reporting.ViewRole
Host-level. Deprecated — kept for backward compatibility only, with no fallback from the tenant setting to it.

AssignViewRoleBackgroundJob

Runs inside currentTenant.Change(args.TenantId). Reads the setting; if it is empty, logs a warning and returns. Verifies the role exists in pg_roles; if not, logs a warning and returns. Then grants SELECT on one view when args.ViewName is set — the automatic path after a successful generation — or on every view in the Reporting schema when it is not.

TenantViewRoleAppService

GetAsync

Returns the saved role, or infers one: {LicencePlate}_readonly from the tenant's LicencePlate extra property, falling back to {tenantname}_readonly when there is no licence plate at all. An explicitly saved role always wins — which is how legacy tenants with non-conforming role names keep working. Also reports live existence of both the read-write and read-only roles.

UpdateAsync

Saves the setting, but only after EnsureRoleExistsAsync confirms the role is real — otherwise UserFriendlyException.

AssignRoleToViewsAsync

Queues the all-views job. It re-checks role existence first deliberately: the background job's own check only logs and silently no-ops, so without this the queue call would report success for a role that doesn't exist.

GetTenantDatabaseInfoAsync

Backs the View DB Info modal — database roles, role memberships, and every view currently in the Reporting schema. Catches and logs on failure, returning empty lists so the UI still renders.

Cross-path

The all-views grant can throw on a database that still holds legacy views. AssignRoleToAllViewsAsync validates every name it reads back from pg_views against ^[a-zA-Z_][a-zA-Z0-9_]*$ before interpolating it into the GRANT — a deliberate injection guard, since quoted PostgreSQL identifiers can contain quotes and semicolons. The deprecated path's view names (Form-…, Worksheet-…, Scoresheet-…) contain hyphens and fail that check, so the loop throws part-way through and leaves the remaining grants unapplied. See the companion handover page.

08

Change detection

A mapping is a snapshot of a source schema. The source can move underneath it — a version is published, a worksheet is unlinked, a form's scoresheet is swapped. DetectChangesAsync is how the administrator finds out.

On load, the provider compares live source state against the Mapping.Metadata.Info keys stored at the last save, and returns a human-readable description string. It lands on ReportColumnsMapDto.DetectedChanges and the UI renders it as an alert. It is advisory — nothing is auto-applied.

09

Known rough edges

Worth knowing before you touch this code.

Real risk

The all-views grant aborts on a legacy view name. Covered in §06 — one hyphenated auto-generated view in the schema is enough to make "assign role to all views" throw, silently leaving later views ungranted. Removing the deprecated path fixes this permanently.

Silent

AssignViewRoleBackgroundJob returns quietly when no role is configured or the role does not exist. TenantViewRoleAppService guards the two paths a user can reach, but a generation-triggered grant has no such guard — a view can be SUCCESS and still unreadable by Metabase.

Asymmetric

Duplicate keys and duplicate paths each only warn; only the two together throw. Deliberate — providers legitimately produce repeated keys across worksheets — but it means a save can succeed with warnings an administrator never sees.

Confusing

The UI column labelled Path shows DataPath, not Path. The real Path is the row-identity key and is never displayed. This trips people up when reading a mapping JSON export against the screen.

Partial cleanup

DeleteAsync and the rename path both downgrade a failed DROP VIEW to a warning. A view can outlive the mapping that created it, after which its name reads as "available" to the correlation-aware check but conflicts on the actual CREATE.

Unwired

ReportColumnsMap.RoleStatus exists on the entity and defaults to NOTASSIGNED, but the grant jobs never write it — role state is only observable in the logs and the DB Info modal.
