Unity.GrantManager

Strip away every module and what remains is a system for receiving grant applications and deciding them. One webhook creates them, a hierarchical fifteen-state machine moves them, assessments judge them, and a dozen flags on a form reconfigure the whole product around them. Everything else — Flex, Payments, AI, Notifications, Reporting — hangs off that spine. This page is the complete reference.

01

The spine

The core is intake, an application record, a review and assessment workflow, a decision, and the applicant and form records those hang off. It is also five to six times the size of the largest module — so it is documented as fifteen focused documents in three tracks, not one narrative.

CHEFS ──webhook──▶ INTAKE submission → Application │ Unity.Flex ──custom fields──▶│ Unity.AI ────analysis/scoring│──▶ APPLICATION 15-state workflow, hierarchical Unity.Notifications ──email──▶│ │ Unity.Flex ────scoresheets───▶ ASSESSMENT 3-state workflow │ ▼ GRANT_APPROVED │ Unity.Payments ◀──approved amount Unity.Reporting ◀─reads everything

Modules are compiled in, not plugged in

The core does not reference modules through interfaces it defines. It takes a direct dependency on each one and wires it in at up to four points — application module, web module, DbContext, and for some the migrator. GrantTenantDbContext.OnModelCreating calls ConfigureFlex(), ConfigureNotifications(), ConfigurePayments(), ConfigureReporting(); GrantManagerDbContext calls ConfigureAI().

The coupling runs both ways — modules reference IApplicationRepository, IApplicationFormRepository and IEndpointManagementAppService as freely as the core references theirs. Treat the core and its modules as one deployable, not a host with plug-ins.

02

Intake

Intake is how a CHEFS submission becomes an Application. It is the only path by which applications are created — there is no manual "create application" screen anywhere in the product.

01 · Webhook

POST api/chefs/event/{__tenant}, [AllowAnonymous]. The body is not trusted as data — Unity takes only the identifiers.

02 · Fetch & validate

Resolve the form by CHEFS GUID, fetch the submission back from CHEFS with the form's own API key, reject drafts and deletions.

03 · Map & create

One transactional unit of work: map to IntakeMapping, create the Application, applicant, agent, attachments, Flex fields.

04 · Publish

ApplicationProcessEvent then ApplicationChangedEvent — both local, both inside the transaction.

Why the transaction matters

The whole creation runs inside one transactional unit of work, and the source comment says why: sequence-number generation for the Unity Application ID needs atomicity. That id is separate from ReferenceNo (always the CHEFS confirmation id) and is generated from the form's configuration:

Prefix == null or SuffixType == null → no Unity ID SuffixType == SequentialNumber → {Prefix}{n:D5} via ISequenceRepository, per prefix digits auto-expand past 99999 SuffixType == SubmissionNumber → {Prefix}{ReferenceNo}

Generation is wrapped in graceful degradation at two levels — a failure inside GenerateUnityApplicationIdAsync is logged and returns null, and a failure escaping it is caught again in CreateNewApplicationAsync with the comment "Application creation is priority". An application is never lost because its id could not be generated.

Two events, four handlers

ApplicationProcessEvent
The declared extension point. Carries the Application, the form version, the submission record and the raw submission. Handlers: DetermineElectoralDistrictHandler, UpdateApplicantProfileCacheHandler (core) and QueueApplicationAIPipelineOnProcessHandler (Unity.AI).
ApplicationChangedEvent
{ Action = Submit, ApplicationId }. Consumed by Notifications' ScheduledNotificationEventHandler to fire configured event-driven email.

Both are local bus events published inside the transaction, so a handler that throws can roll back the entire intake.

Things intake deliberately tolerates

  • A missing supplier. RelateDefaultSupplierAsync is wrapped in a bare try/catch at the call site — the comment records SSL certificate errors reaching CAS, and intake must not block on it.
  • Bad field values. MappingUtil coerces defensively — ResolveAndTruncateField(255, …), ConvertToDecimalFromStringDefaultZero, ConvertDateTimeFromStringDefaultNow. Bad or missing values become defaults, not failures.
  • An unmapped form version. The mapping lives on the matching ApplicationFormVersion; a version Unity has never seen yields no map and the mapper falls back to its defaults. See §05.
  • A rejected submission. Drafts and deletions notify a Teams channel and return a 200 with a failure body rather than an error.

The nightly resync reports; it does not import

IntakeSyncWorker runs twice daily (0 0 7,19 1/1 * ? * — 11 PM and 11 AM Pacific) looking back four days, and calls GetMissingSubmissions per tenant. If anything is missing and ASPNETCORE_ENVIRONMENT is exactly Production, it emails one summary to a hard-coded address. Recovering a missed submission is a separate, manual action.

03

The workflow

Fifteen states would be unreadable as a flat table. They are not flat: two superstates carry the transitions every open or resolved application shares, and that is the structural fact that makes the rest comprehensible.

OPEN superstate · initial transition → SUBMITTED
Pipeline SUBMITTED ASSIGNED UNDER_INITIAL_REVIEW INITITAL_REVIEW_COMPLETED
UNDER_ASSESSMENT ASSESSMENT_COMPLETED
Parking DEFER ON_HOLD
Every substate inherits Withdraw, Close, Internal_Unasign — and, when the form allows it, direct Approve/Deny. That inheritance is why those transitions are not repeated eleven times.
RESOLVED superstate · no transitions of its own — a grouping
Decided GRANT_APPROVED GRANT_NOT_APPROVED
Ended CLOSED WITHDRAWN
Neither is terminal. DEFER and ON_HOLD return to any point in the pipeline and to each other; CLOSED and WITHDRAWN reopen. Only one transition in the whole machine is permission-guarded: deferring an already-approved grant, which needs Approvals.DeferAfterApproval.

Configured on the service, not the entity

ApplicationManager.ConfigureWorkflow(stateMachine, isDirectApproval) lives on the domain service because it needs repositories and a permission checker — unlike the assessment machine, which lives on its entity. Both sit behind the shared UnityWorkflow<TStates, TTriggers> wrapper over Stateless, which throws BusinessException("InvalidStateTransition") for anything not permitted. GetWorkflowDiagram(isDirectApproval) renders the configured machine as a Mermaid graph — the fastest way to check the effect of a change.

Direct approval is a per-form flag passed into that method. It unlocks Approve/Deny from OPEN — and therefore from every open substate — plus from CLOSED and WITHDRAWN. The guard stateMachine.State != targetState exists solely to prevent approving an already-approved application.

The status is a table, not a column

The application stores ApplicationStatusId, a foreign key into the tenant's ApplicationStatus table. The workflow runs against a local copy of the status code purely as a gate; the real write resolves the row afterwards. The enum carries a warning that its numbering is load-bearing: // WARNING: DO NOT EDIT ORDER NUMBER WITHOUT UPDATING DB CODE TABLE.

Assignments drive two automatic transitions

Two rules, called out in comments across four methods: an application in SUBMITTED with a user assigned moves to ASSIGNED; an application with all assignees removed returns to SUBMITTED. They fire Internal_Assign / Internal_Unasign — two of the four Internal_ actions, which GetActions flags and hides from the UI by default. An owner is separate from assignees and does not affect state.

Field updates are tiered by permission

The entity exposes no public setters for the fields that matter. It exposes four grouped update methods, and the grouping is the authorization model.

MethodFieldsWhen
UpdateAlwaysChangeableFieldsNotes, SubStatus, LikelihoodOfFunding, TotalProjectBudget, NotificationDate, RiskRankingAny time
UpdateFieldsOnlyForPreFinalDecisionDueDiligenceStatus, RecommendedAmount, DeclineRationalBefore a final decision only
UpdateApprovalFieldsRequiringPostEditPermissionApprovedAmountNeeds a post-decision override
UpdateAssessmentResultFieldsRequiringPostEditPermissionRequestedAmount, TotalScoreNeeds a post-decision override

Entity-level validators sit alongside: a due date cannot be more than a day in the past, a final decision date cannot be in the future, an approved amount cannot be zero, and a recommended amount cannot be zero unless the form is direct-approval. All compare against the current value first, so re-saving an unchanged field never fails validation.

04

Assessment

One assessor's review of one application. Many per application, at most one per assessor, at most one generated by AI. Three states, and — uniquely in the core — the workflow lives on the entity.

IN_PROGRESS ──Complete──▶ COMPLETED ──SendBack──▶ IN_PROGRESS ▲ IN_REVIEW ────Complete────────┘ (legacy — nothing transitions INTO it) IN_REVIEW ────SendBack────▶ IN_PROGRESS

The entry and exit hooks on COMPLETED are the only place IsComplete and EndDate are written. Note the asymmetry: OnReopened clears EndDate but leaves IsComplete true.

Creating one has consequences elsewhere

AssessmentManager.CreateAsync rejects a second assessment for the same user and any assessment on an application in a final decision state. Then two side effects fire:

First human assessment
Moves the application to UNDER_ASSESSMENT via Internal_StartAssessment — but guarded by IsActionAllowed first, so an application already past that point is not dragged backwards. hasOtherAssessments excludes AI assessments, so an existing AI record does not suppress the transition.
Flex scoresheet instance
Published as CreateScoresheetInstanceEto when the form has a ScoresheetId and the Flex feature is on. RelatedCorrelationId points at the first existing assessment's instance — how Flex relates parallel assessments of one application.

AI assessments are a narrower path

CreateAiAssessmentAsync is idempotent, takes no user, and does not touch application state. Its assessor is AIScoringConstants.AiPersonId — the fixed GUID 00000000-0000-0000-0000-000000000001, seeded as one AI Scoring Person per tenant so it satisfies the same foreign keys a human does. The record is created directly as COMPLETED.

It is read-only, enforced twice: ExecuteAssessmentAction throws CannotModifyAiAssessment, and AssessmentAuthorizationHandler short-circuits on IsAiAssessment before any ownership check. An assessor who wants to build on it calls CloneFromAiAsync, which creates an ordinary assessment for them through the normal manager — same rules, same one-per-user constraint — and copies the scoresheet answers across.

Resource-based authorization

This is one of the few places in the codebase using ABP's AuthorizationService.CheckAsync(resource, requirement) rather than a static policy. The requirement name is composed at runtime from a selector prefix plus the workflow action:

Name = $"{UnitySelector.Review.AssessmentReviewList.Update.Default}.{triggerAction}"

The handler's key rule is ownership — resource.AssessorId == currentUserId || resource.CreatorId == currentUserId. An assessor may act on their own assessment; acting on someone else's requires the broader permission. Completing also runs ValidateAnswersOnCompleteAsync, which blocks the transition when the Flex scoresheet is not adequately answered.

Two scoring systems coexist. Flex scoresheets are current and flow back to Application.TotalScore. The four fixed integer fields on the assessment — FinancialAnalysis, EconomicImpact, InclusiveGrowth, CleanGrowth — predate them and carry their own note: "need to revisit scoring again post-MVP as right now it is only offline scoring". Assessment results are a third thing again, and live on the application, not the assessment.

The mapping is per version, not per form

This is the single most important thing about form versions, and the source of the quietest failure mode in the product.

submission.formVersionId ↓ ApplicationFormVersion where ChefsFormVersionGuid == formVersionId ↓ SubmissionHeaderMapping → IIntakeFormSubmissionMapper.MapFormSubmissionFields

A submission arriving for a CHEFS version Unity has never seen resolves to no mapping, and the mapper falls back to defaults. The application is still created — only the fields the defaults cover are populated. Publishing a new version in CHEFS without mapping it in Unity degrades quietly rather than failing.

Synchronising with CHEFS

ApplicationFormSycnronizationService (the misspelling is in the type name) owns the pull side: connected forms, what CHEFS holds, what Unity holds, and the set difference. Two behaviours worth carrying: requests are paced at 500 ms (ChefsRequestPacingDelay) so a sweep across many forms does not hammer CHEFS, and authentication is per form — the encrypted ApiKey used as basic auth with the CHEFS form GUID as username. There is no tenant-wide CHEFS credential.

The AI-assisted mapping workflow

ApplicationFormVersionAppService is 1,258 lines and does two distinct jobs: version lifecycle, and the human side of AI form generation. AI writes mapping suggestions, draft worksheets and draft scoresheets; this service is where a person accepts or discards them, phase by phase through FormMappingReviewPhase.

Nothing AI produces reaches a form without passing through one of these accept methods.

External links have a hard cap

SetExternalLinks replaces the whole set atomically, enforces MaxRelatedExternalLinks = 8, and stamps the link types itself so callers cannot mislabel them. Its validation intent: nothing can be marked visible to applicants without somewhere to go.

06

Permissions & zones

Unity's authorization is finer-grained than most ABP applications: permissions do not stop at "can open the applications page", they reach individual fields and widgets. One constants tree does the work, and each of its strings does three jobs at once.

One string, three jobs

UnitySelector — 271 lines, 111 constants, three partial-class files — states its own intent: conventional semantics around actions, permissions, zones, and front-end element IDs.

"Unity.GrantManager.ApplicationManagement.Applicant.Summary" ├─ permission name → [Authorize(...)] and the role editor ├─ zone name → DefaultZoneDefinition, IZoneChecker └─ .ElementId() → Unity_GrantManager_..._Summary (DOM id)

Top-level groups: Applicant, Application, Review, Project, Funding, Payment, ApplicantManagement, SettingManagement — each leaf carrying the conventional Default/Create/Update/Delete quartet. GetAll() enumerates the tree by reflection so the permission definition provider never lists it twice.

The Override file adds a further tier — permissions that let a user do what the normal rules forbid: editing approval or assessment-result fields after a final decision, setting the renewal flag, reassigning an application's applicant. The entity groups fields by when they may be edited (§03); these permissions decide who may edit them outside that window.

Zone configuration is a setting, not a table

ZoneManager serialises the whole ZoneGroupDefinition into one ABP setting, GrantManager.UI.Zones, and reads it with fallback: true. That gives the resolution order for free:

form ("F" + formId) → tenant → DefaultZoneDefinition.Template

Nothing has to be seeded for the screen to work, and a corrupt or unparseable setting falls back to the default template rather than throwing. Three properties are [JsonIgnore] and never persisted — ViewComponentType, ElementId, IsConfigurationDisabled — so the stored configuration holds only what an administrator can actually change. GetStateSetAsync flattens it to one HashSet<string>, which is why a zone inside a disabled tab is excluded entirely, regardless of its own flag.

[Authorize(UnitySelector.Review.AssessmentResults.Update.Default)] — the common case, applied per app-service method rather than per class. That is how field-level editing rights are enforced.

Eleven roles; PermissionGrantsDataSeeder (393 lines) seeds ten of them — every value except financial_analyst, whose grants come from elsewhere. The three approver roles get their PaymentsPermissions.Payments.L*ApproveOrDecline grants here, which is how a module's permissions reach a core role. Unity replaces ABP's PermissionDataSeeder outright so the seed runs inside CurrentTenant.Change and inserts only what is not already granted — making re-seeding idempotent and tenant-correct.

Features are a separate axis from permissions. A feature says what the tenant has; a permission says what the user may do. Most module permissions are declared .RequireFeatures(...), so turning a feature off also removes its permissions from the role editor.

07

Two databases

Unity is multi-tenant with a separate PostgreSQL database per tenant, plus one host database. Everything about persistence follows from that — including the most common mistake anyone makes in this codebase.

GrantManagerDbContext — host

ConnectionStringName("Default"), and it replaces ABP's IIdentityDbContext and ITenantManagementDbContext.

  • Tenants, users, roles, permissions, settings
  • Audit logs, background jobs
  • DynamicUrls, CasClientCodes, TenantTokens
  • ApplicantTenantMaps, locality reference data
  • InboxMessages / OutboxMessages
  • ExceptionLogs
  • AI config: AIModels, AIOperations, AIPrompts, AIRequests

GrantTenantDbContext — one per tenant

OnModelCreating is 523 lines: ~30 explicit configurations, then every module's model extension.

  • Applications, applicants, forms, assessments
  • Attachments, comments, tags, history
  • Payments.*, Flex, Notifications.*, Reporting
  • AI's tenant tables: GenerationReviews, ApplicationScoresheetAnswers

A module that does not appear in that extension list has no tenant tables — which is why ConfigureAI() is called on the host context instead.

The AI schema exists in both databases holding different tables. Choosing the wrong migration folder is the most common mistake when adding one:

dotnet ef migrations add <Name> --context GrantManagerDbContext --output-dir Migrations/HostMigrations dotnet ef migrations add <Name> --context GrantTenantDbContext --output-dir Migrations/TenantMigrations

Provisioning a tenant database does more than migrate

MigrateAsync(Tenant?) reads the tenant's connection string and decrypts it, validates that Database, Username and Password are all present, builds an admin connection string and retargets a resolved context at it, grants schema privileges to the tenant role, ensures and reconciles the migration history table, migrates, grants table privileges — then repeats the privilege grants for the read-only connection string if the tenant has one. That read-only role is what Reporting and Metabase connect through.

The Database:FlattenMigrations mechanism exists for one specific problem: a database provisioned before the migrations were squashed has history rows predating Initial, so MigrateAsync would try to re-run Initial against a schema that already has those tables. ReconcileMigrationHistoryAsync writes the Initial row in first so EF skips it.

Tenancy is ABP's filter, not hand-written WHERE clauses

Nearly every core entity is IMultiTenant and no core query filters on TenantId by hand. Stepping outside it is explicit — ICurrentTenant.Change(tenantId), almost always a background worker sweeping every tenant. The one entity that deliberately avoids a global filter is Applicant: it declares its soft-delete fields manually rather than implementing ISoftDelete, because that filter would apply to Include() joins and silently drop Application rows whose applicant was deleted, breaking the application and payment lists.

The rule that follows: any new query listing applicants needs its own !a.IsDeleted; any query loading applications through applicants must not have one.

Cold start is a designed-around problem

GrantManagerDbWarmupService documents the cost precisely: on first use EF compiles the model, translates the LINQ tree — expensive for the multi-join application list — and establishes the Npgsql pool, together 6–8 seconds on the first application list request. Phase 1 (model compilation) needs no database and always succeeds; phase 2 walks the tenants warming Npgsql's pool and Postgres' plan cache, and can be disabled.

Other Postgres specifics worth knowing: Npgsql.EnableLegacyTimestampBehavior is switched on, so timestamp without time zone is used throughout; jsonb carries the semi-structured payloads (Application.Payload, FormSchema, ReviewData, Answers); and tests run on SQLite in-memory, which is why repository code sticks to translatable LINQ.

08

The platform

What people attach to an application and record around it, and the machinery underneath: attachments, comments and tags, three unrelated things called history, the integration layer, and everything that runs without a user.

Attachments: two storage paths

CHEFS-held

Uploaded by the applicant in CHEFS; the content stays in CHEFS and is fetched on demand. ApplicationChefsFileAttachment extends AbstractAttachmentBase and carries ChefsSubmissionId, ChefsFileId — and AISummary, where the AI module writes its attachment summary.

S3

Uploaded by staff in Unity. ApplicationAttachment, AssessmentAttachment, ApplicantAttachment extend AbstractS3Attachment, stored through ABP's IBlobContainer via S3BlobProvider — an S3-compatible store, path-style, no AWS region.

Preview converts anything not browser-viewable to PDF by shelling out to /usr/bin/libreoffice — the only place in the product that invokes an external process. IsInstalled() lets callers degrade where the container image lacks the binary. AttachmentController, at 769 lines, is the largest controller in the product and serves both staff and the applicant portal, so its authorization is per-endpoint rather than class-wide.

Tags are shared with Payments — so deletion is an event

One Tag table, two join tables: ApplicationTags (core) and PaymentTags (Unity.Payments). That sharing is why ConfigurePayments() re-declares the core's Tag mapping, and why deleting a tag cannot be a foreign-key cascade:

TagsAppService.DeleteTagAsync ↓ publish DeleteTagEto { TagId } ← the REQUEST to remove usages Payments DeleteTagHandler → PaymentTagAppService ↓ publish TagDeletedEto ← the CONFIRMATION it was done core TagDeletedHandler → clean up application tags

Two deliberately distinct event types. Note also that applying a tag is gated separately from administering one — a user can be allowed to tag applications without being allowed to create tags, and vice versa.

Comments share one CommentBase across three subjects (application, assessment, applicant), each its own table with its own repository. Every CommentsManager method takes ownerId alongside commentId, so a comment id from one application cannot reach a comment on another. @-mention email is one of only two paths in the product that bypass the queued email pipeline and call CHES directly — the other is exception alerts.

There is a fourth kind again in the UI: EmailHistoryWidget reads the Notifications module's EmailLog.

Every external URL is a database row

No external base URL is a constant or a configuration key. DynamicUrlKeyNames lists them — CHEFS, CSS and its token endpoint, CAS, CHES, OrgBook, Geocoder, Metabase, Matomo, GitHub — resolved at runtime through IEndpointManagementAppService. Two keys are prefixes: DIRECT_MESSAGE_ and WEBHOOK_ take numerically incremented suffixes, so an operator can add another Teams channel without a code change.

Repointing an integration is a data change, not a deployment. That is the design intent, and it is why environment-specific URLs do not appear in appsettings. A missing row raises UserFriendlyException, which is why several callers wrap the lookup and degrade instead of failing.

Background work sweeps tenants serially

Quartz workers start with no tenant context, so every one that touches tenant data follows the same shape — load all tenants, using (_currentTenant.Change(...)) per tenant. Two consequences: the work is serial, so a slow tenant delays the rest; and an unhandled exception inside the loop aborts the remaining tenants unless the worker catches per tenant. Cron expressions come from settings, changed through the admin UI rather than a deployment.

Exception alerting has two collectors and one throttle

ABP-handled exceptions ──▶ AbpExceptionNotificationSubscriber (IExceptionSubscriber) │ exceptions bypassing ABP ──▶ ExceptionCounterMiddleware ▼ ExceptionNotificationThrottle per-type cooldown · global cap 5 per minute ▼ GitHubBlameLookupService ──▶ who last touched the line ▼ Teams webhook (DIRECT_MESSAGE_* dynamic URL)

Both collectors are needed: ABP handles most exceptions before they reach middleware, so the subscriber sees those, while the middleware catches only what bypasses ABP. The throttle exists, in its own words, to "prevent Teams notification storms during an outage". Separately, ExceptionLog rows carry a five-day per-exception suppression window on their alert email.

The metrics endpoint is authorized, not public — MapMetrics().RequireAuthorization(PolicyRegistrant.MetricsAccessPolicy). And en-CA is the only supported culture, for both supported and UI cultures.

09

Known rough edges

The core has no roadmap document of its own; this is what the fifteen documents surfaced, ordered by real-world risk. Much of it is correct but surprising rather than defective — but the first several will cost someone a day if they meet them cold.

Real risk

Payment history is joined by hard-coded type names. HistoryConsts pins "Unity.Payments.Domain.PaymentRequests.PaymentRequest" and …ExpenseApproval as strings in the core. Renaming or moving either Payments class silently empties the Payment History page. Nothing at compile time connects them.

Real risk

An unmapped form version degrades silently. The submission mapping is per version. Publish a new version in CHEFS without mapping it in Unity and applications still get created — with only the fields the mapper's defaults cover. There is no failure, no alert, and the gap is visible only as blank fields on new applications.

Real risk

The intake resync tells nobody outside production. IntakeSyncWorker emails its missing-submission summary only when ASPNETCORE_ENVIRONMENT is exactly "Production". Everywhere else it detects the gap and stays silent. The recipient, sender and subject are hard-coded in the worker, and the worker only reports — importing the missed submission is a separate manual action.

Multi-pod

InMemoryDistributedLockProvider satisfies the interface, not the guarantee. It is a ConcurrentDictionary of semaphores — per process. In a multi-pod deployment each pod holds its own dictionary, so a lock taken on one does not exclude the other. Anything relying on a lock for correctness across pods needs the real provider configured.

Environment

PDF preview shells out to a hard-coded binary path. /usr/bin/libreoffice, the only external process the product invokes. Any container image without LibreOffice loses preview for non-browser-viewable attachments — IsInstalled() degrades gracefully, so the symptom is a missing feature rather than an error.

Silent

Intake swallows two failures by design. The default-supplier link is caught and logged (SSL certificate errors reaching CAS), and MappingUtil converts unparseable values to zero, empty or Now. Both are deliberate — intake must not fail — but neither leaves a mark on the application that a reader would notice.

Silent

A rejected CHEFS submission returns HTTP 200. Drafts and deleted submissions notify Teams and return an EventSubscriptionConfirmationDto carrying an exception message — so CHEFS records a successful delivery either way.

Coupling

Two enum orderings are load-bearing against database rows. GrantApplicationState carries // WARNING: DO NOT EDIT ORDER NUMBER WITHOUT UPDATING DB CODE TABLE — the status is stored as a foreign key into a per-tenant ApplicationStatus table, not as the enum value. And INITITAL_REVIEW_COMPLETED is misspelled in the enum and in the matching code-table row, so it cannot be fixed on one side alone.

Coupling

Intake resolves the form by "first match, oldest first". The ApplicationForm whose ChefsApplicationFormGuid matches, ordered by CreationTime, taking the first. Two forms bound to the same CHEFS form is not rejected anywhere — it just routes every submission to the older one.

Legacy

Dead paths kept for data compatibility. AssessmentState.IN_REVIEW has transitions out and none in, kept only so existing rows stay valid — its own comment says it will be removed once none are left. AssessmentAction.Create is declared but never configured as a trigger. And Tags.cs declares a second, near-identical Tags aggregate alongside Tag; only Tag is referenced by the join tables.

Legacy

Two scoring systems and an unfinished note. The four fixed integer fields on Assessment predate Flex scoresheets and are still written by UpdateAssessmentScore, which carries its own TODO: "need to revisit scoring again post-MVP as right now it is only offline scoring — need to leverage state machine and domain layer during the revisit." Reopening a completed assessment also clears EndDate but leaves IsComplete true.

Size

Four files carry a disproportionate share of the core. GrantApplicationAppService (1,388 lines, GetListAsync alone 250), ApplicationFormVersionAppService (1,258, doing two unrelated jobs), AttachmentController (769) and GrantManagerWebModule (738). ApplicationRepository (677) holds the widest read path in the product.

Duplication

Types that exist twice. MatomoUrlProvider in both Application/Analytics/ and Web/Analytics/ — the web copy is the one the layout uses. And Unity.Payments keeps a near-identical private copy of the UnityWorkflow wrapper as PaymentsWorkflow.

Convention drift

Misspellings baked into public type and method names — ApplicationFormSycnronizationService, ZoneManager.SetForTennantAsync. DateTime.UtcNow used inline in ApplicationManager rather than IClock, alongside a hand-set LastModificationTime carrying the comment "This was not being updated". And intake writes the application row, then sets ApplicantId in a second write once the applicant resolves.

Fragility

Local events inside the intake transaction. ApplicationProcessEvent and ApplicationChangedEvent are published before the unit of work is saved, so a throwing handler — in the core, in AI, in Notifications — rolls back the entire intake. That is a real coupling between module handler code and whether an application can be received at all.
